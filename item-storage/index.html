    Item persistence engine¶

    Decision¶

    Item definitions (base, affix metadata, localization, ranges and tags) are immutable content addressed by stable uint32 IDs. An item instance stores only identity, ownership/location, version, stack, compact mutable values, RNG seed and rolled affix ID/value pairs. This avoids repeating strings and definition data in every dropped item.

    server/internal/itemstore is the adapter boundary. Game rules depend on Store, not on a database driver. Memory is an executable specification and test backend; it is not the production MMO database.

    Database topology¶

    • Solo/local/offline: SQLite in WAL mode is the preferred durable adapter. Use one writer transaction, prepared batch statements and periodic checkpoints. It is embedded, recoverable and requires no service. A SQLite driver should be chosen only when the adapter is implemented; avoid adding CGO or a large dependency before then.
    • Authoritative coop/PvP: PostgreSQL-compatible SQL is the preferred model. It provides row locking, transactional crafting/transfers, mature replication/backup and operational tooling. Partition by account/owner only after measurements require it. Do not use SQLite as a shared network filesystem database.
    • Redis is optional later for short-lived caches/locks, never the source of truth for owned items.

    The DB row keeps queryable ownership/location/version columns and a compact versioned payload for less frequently queried instance state. Do not put the entire item in JSON.

    CREATE TABLE item_instance (
  item_id BIGINT PRIMARY KEY,
  definition_id INTEGER NOT NULL,
  owner_kind SMALLINT NOT NULL,
  owner_id BIGINT NOT NULL,
  location_kind SMALLINT NOT NULL,
  container_id INTEGER NOT NULL DEFAULT 0,
  grid_x SMALLINT NOT NULL DEFAULT 0,
  grid_y SMALLINT NOT NULL DEFAULT 0,
  slot SMALLINT NOT NULL DEFAULT 0,
  stack_count INTEGER NOT NULL CHECK (stack_count > 0),
  version BIGINT NOT NULL,
  payload BYTEA NOT NULL
);
CREATE INDEX item_owner_location
  ON item_instance(owner_kind, owner_id, location_kind, container_id, item_id);
CREATE TABLE item_operation (
  owner_id BIGINT NOT NULL,
  operation_id UUID NOT NULL,
  result BYTEA,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY(owner_id, operation_id)
);

    SQLite uses equivalent INTEGER/BLOB columns. item_operation keys make retried network requests idempotent; production adapters must retain or archive them for at least the maximum retry window.

    Atomic operations¶

    Transfer, equip, salvage and craft execute inside Store.Transact. Reads and writes use version as an optimistic concurrency token. A transfer updates owner and location in one transaction. Crafting consumes materials and changes/creates the result in the same transaction, so disconnects cannot duplicate items. Stack split/merge is likewise one transaction: validate matching definition and stackable state, decrement/delete the source, then increment/create the destination.

    The in-memory implementation serializes transactions for correctness. A SQL adapter should use SELECT ... FOR UPDATE in stable item-ID order to avoid deadlocks and UPDATE ... WHERE item_id=? AND version=? to detect stale clients.

    Encoding and migrations¶

    The payload starts with a codec version and uses unsigned varints plus zig-zag signed roll values. Natural boolean state shares a uint16 flags field. Everything else remains explicit: manual cross-field bit packing is deliberately omitted because it complicates migrations and debugging while database row/index overhead usually dominates a few bytes.

    Never reuse definition IDs. Content revisions either remain backward-compatible or migrate records in resumable batches. Decoder support for the previous version must remain during rolling deployment; backfills write the new version, verify counts/checksums, then retire old decoding in a later release.

    Capacity and observability¶

    Load inventory pages by indexed owner/location key, never all world items. Batch gets preserve the requested ID order among found records; list pagination uses monotonic item_id, not offsets. Cache immutable definitions globally and small active inventories per session. Track transaction latency, conflict rate, payload bytes/item, rows read, idempotency hits and craft/transfer failure reasons.

    Run measurements with:

    go test ./internal/itemstore
go test -run '^$' -bench BenchmarkCodec -benchmem ./internal/itemstore
go test -run '^$' -bench BenchmarkEncodeMillion -benchtime=1x -benchmem ./internal/itemstore

    The million-item benchmark is intentionally opt-in because it allocates a large synthetic fixture. Results are machine-specific and should be recorded in release/performance notes rather than hard-coded as promises.
