    Codex GPT (gpt-6-astra) design consult - COD-25 actions (recovery, cancellation, order), 2026-09-05¶

    Non-normative. Brief: problem-only, project brief prepended; Codex did not read the repo. Not yet verified against source by a scout. Open for the owner: the two unnamed "generator acceptance tests" in the card (Codex: drop them), golden trace + simulation_version bump.

    Рекомендация: оставить один inline Action, добавить идентификатор экземпляра и recovery. Отдельный список экземпляров сейчас не нужен. Два неназванных генераторных теста убрать из критерия готовности: они не определяют проверяемый результат этой карточки.

    Ниже — предложения на основе переданных фактов; файлы самостоятельно не читал.

    1. Модель и порядок экземпляров

    В Action добавить:

    InstanceID        uint64
Recovery         uint32
RecoveryRemaining uint32

    Типы счётчиков желательно согласовать с существующим WindupRemaining; uint32 здесь — предложение. В состояние симуляции добавить NextActionInstanceID, в ActionPhase — PhaseRecovery = 4, сохранив прежние значения.

    • InstanceID = 0 означает отсутствие активного экземпляра.
    • ID выдаётся при принятии действия к подготовке, а не при каждом повторном выборе.
    • Выдача последовательная, начиная с 1; несколько стартов одного тика обрабатываются по возрастанию EntityID.
    • Все impacts одного тика исполняются по возрастанию InstanceID. Ни тип эффекта, ни текущий порядок обхода сущностей не меняют эту очередь.
    • При завершении экземпляра его поля очищаются по одному правилу. Счётчик не откатывается.

    Это порядок создания экземпляров: более старый windup при совпадении тика impact исполняется раньше. Он полностью восстанавливается из канонического состояния. Ключи (EntityID, InstanceID) и (creationTick, EntityID) не нужны.

    Перед stage 5 можно собрать временный срез готовых действий и отсортировать его. Он не является состоянием и не сериализуется. Постоянный список понадобится лишь при разрешении нескольких одновременно живущих действий одного владельца.

    1. Отмена, interruption и recovery

    Разделить три причины:

    • Невалидная цель: симуляция автоматически завершает подготовку с ActionFailed(TargetInvalid).
    • Намеренная отмена: детерминированная команда от будущего Brain; сейчас достаточно узкого входа, доступного фиксированному сценарию и тестам. Команда адресует InstanceID, чтобы старая отмена не задела новое действие.
    • Прерывание попаданием: оставить будущему stagger. Само получение урона не прерывает windup. Смерть владельца прекращает его ещё не исполненное действие.

    Минимальная предлагаемая форма события:

    ActionFailed {
    Tick,
    ActorID,
    TargetID,
    InstanceID,
    Reason: TargetInvalid | Cancelled | ActorDead
}

    Отдельные ActionCancelled и ActionInterrupted сейчас не нужны. Interrupted добавить вместе с правилами stagger. Событие реализованного эффекта должно содержать тот же InstanceID; не требуется отдельное событие начала recovery, если его однозначно определяет результат исполнения.

    Отмена допустима в PhasePending/PhaseWindup и до начала атомарного исполнения. Внутри исполнения отмены нет. После эффекта действие обязано перейти в recovery.

    Recovery:

    • фиксированная длительность конкретного действия, захваченная при старте;
    • для этого среза — целое положительное число тиков; конкретные длительности требуют данных баланса;
    • не отменяется командой Brain, уроном или сменой цели;
    • не делает владельца неуязвимым, нетаргетируемым или неподвижным: его можно атаковать и толкать;
    • смерть владельца прекращает существование действия, а не выдаёт ему возможность действовать без оплаты recovery.

    Нулевой нанесённый урон сам по себе не означает неудачу исполнения. Валидно исполненная атака с нулевым результатом оплачивает recovery. Невалидная до исполнения цель — нет.

    1. Место внутри тика

    Полный состав десяти стадий не дан, поэтому назначать остальным номера нельзя. Сохранить существующий stageOrder, встроив операции в известные точки:

    advanceActionTimers:
    применить адресные отмены подготовки
    прекратить подготовку при смерти владельца / невалидной цели
    уменьшить существовавшие на входе таймеры windup и recovery
    завершить recovery, если остаток стал 0

startSelectedActions:
    для доступных сущностей принять существующий фиксированный выбор
    проверить владельца и цель
    выдать InstanceID; начать windup

resolveImpacts — stage 5:
    собрать готовые экземпляры; сортировать по InstanceID
    перед КАЖДЫМ исполнением повторно проверить владельца и цель
    исполнить атомарно; затем установить recovery

    stageDecisions оставить заглушкой. Новый Brain для выбора следующего действия не нужен: используется уже существующая фиксированная выборка.

    Детали границ:

    • После завершения recovery новое действие разрешено в startSelectedActions этого тика.
    • После отмены — со следующего тика. Это можно обеспечить временной отметкой внутри тика; новое каноническое поле не требуется.
    • Recovery, созданный stage 5, впервые уменьшается на следующем тике. При Recovery = R и impact на тике t следующий старт возможен на t + R.
    • Существующую семантику первого уменьшения windup и нулевого windup сохранить и закрепить тестом.

    Нельзя заранее считать все цели валидными на весь stage 5, группировать эффекты по типам или заранее бросать RNG на всю очередь. Более ранний impact может сделать следующий экземпляр неисполняемым.

    Предлагаемая политика смерти: если ранний impact убил владельца позднего действия, позднее действие не исполняется. Это последовательное разрешение внутри тика; его нужно явно закрепить в спецификации.

    1. Каноническое состояние, версии и проверки

    Канонизировать четыре новых значения: Action.InstanceID, Action.Recovery, Action.RecoveryRemaining, NextActionInstanceID. Phase уже сериализуется. Не добавлять creationTick, дублирующий флаг busy или постоянную очередь impacts.

    • simulation_version: 10 → 11.
    • canonical_state_version: увеличить на 1 от текущего значения, которое здесь не приведено.
    • Обновить правила несовместимости записей согласно существующей политике.
    • Новый golden разместить под версией 11 по принятой в репозитории схеме; не перезаписывать v10 как будто поведение прежнее.

    Перед согласованием golden вручную проверить короткий сценарий: тик старта, выдачу ID, тик каждого impact, порядок совпавших impacts, причину каждой отмены, отсутствие запрещённых RNG-вызовов, начало/конец recovery, терминальный результат и количества событий/снимков. Затем проверить соответствие checkpoint-хешей утверждённому каноническому кодированию. SHA-256 нельзя содержательно проверить глазами: ручное согласование относится к поведению и формату, а не к внешнему виду хеша.

    Golden оставить как интеграционный контроль. Добавить рядом с Go-кодом адресные тесты:

    • реализованный эффект переводит действие в recovery ровно один раз;
    • отменённый экземпляр не производит эффект, recovery или RNG-вызов;
    • после эффекта команда отмены не сокращает recovery;
    • смерть цели между двумя impacts даёт второму TargetInvalid, без броска;
    • попадание без stagger не отменяет windup;
    • старый экземпляр сущности с большим ID исполняется раньше нового экземпляра сущности с меньшим ID;
    • не влияющий на результат бонус не потребляет RNG;
    • остальные стадии не меняют состояния RNG;
    • одинаковая капсула даёт одинаковые ежетиковые хеши, события и итог, включая запуски отдельными процессами;

    • состояние счётчика ID входит в канонический хеш, даже когда активных действий нет.

    • «Два генераторных теста»

    Формулировку карточки исправить. Сейчас это неназванная зависимость, а не acceptance criteria.

    Предложение (a) смешивает генерацию, достижимость, выбор цели, передвижение и длительности действий. Без их контракта условие «каждая сущность завершает цикл за N» произвольно; в настоящем бою сущность ещё и может погибнуть раньше.

    Предложение (b) требует действия с толчком, потребителя NominalPushEntersVoid и контракта смерти в void. Оно принадлежит интеграции арены с действиями, а не добавлению recovery.

    Для этой карточки заменить их двумя конкретными тестами жизненного цикла:

    • Фиксированная допустимая цель: windup → impact → recovery → следующий разрешённый старт; проверяются точные тики.
    • Два готовых экземпляра: первый делает цель второго невалидной; проверяются порядок ID, ActionFailed(TargetInvalid), отсутствие recovery и RNG у второго.

    Если генераторные тесты действительно обязательны, сначала нужны их отдельные спецификации и зависимости. Объявлять их выполненными этими двумя тестами нельзя.

    1. Минимальный объём карточки

    Включить inline-экземпляр с ID, recovery, адресную отмену подготовки, автоматическое завершение при невалидной цели/смерти владельца, сортировку stage 5, события, канонизацию, версии и проверки выше.

    Оставить:

    • COD-24: девять стадий stat pipeline, модификаторы длительностей, расчёт боевых результатов. Сейчас сохранить существующий единственный бросок; не добавлять предварительную «проверку успеха».
    • Brain: восприятие, выбор, решение отменять и повторно выбирать действие, AI tie-break.
    • Последующим карточкам: stagger, толчки в void, кактусы, bleed, лимит постоянных hazards.

    Исправленный done-when: «Recovery и отмена подготовки реализованы; impacts исполняются по InstanceID; одинаковая капсула воспроизводит одинаковое состояние и события; адресные тесты и согласованный golden проходят». При неизменном требовании неназванных генераторных тестов карточка остаётся недоопределённой.

    1. Противоречия и главные риски

    2. TargetInvalid против намеренного финта. Если запись в open-questions.md требует этот reason для любой отмены подготовки, она смешивает разные причины. Предлагаю Cancelled для намеренной отмены; это изменение нормативного текста, которое нельзя внести молча.

    3. «Подготовка допускает interruption» против отсутствующего stagger. Отмена жизненного цикла не реализует прерывание ударом. Если последнее входит в done-when, нужны отдельные правила воздействия.
    4. Стабильный порядок не определяет политику смерти автоматически. Предложенное прекращение действий погибших владельцев — дополнительное решение, а не приведённый факт.
    5. Заявленная разблокировка генератора не подтверждена контрактом тестов. Само добавление recovery не создаёт потребителей void-предикатов.
    6. Любая отмена, меняющая число бросков, сдвигает последующую последовательность. Это ожидаемое изменение версии симуляции; внутри новой версии порядок и условия бросков должны быть неизменными.

    Assumptions¶

    • Одновременно у сущности живёт не больше одного действия; независимых от владельца летящих эффектов в этом срезе нет.
    • Намеренная отмена поступает из детерминированного сценария/Brain, без ввода игрока во время боя.
    • Длительности recovery будут заданы в данных действий; чисел баланса в исходных фактах нет.

    Round 2 (same thread) - answers to the source-verified gaps, 2026-09-05¶

    Round-1 claims were checked against server/internal/sim by a read-only agent; four were wrong (unknown target is a hard tick error, dead actor/target is a silent fizzle; EntityID order is the declared tie-break of every stage; both versions are 10; the golden has no regenerator). Codex was sent the facts and asked for one codable answer per gap. Owner accepted all nine below as the COD-25 decisions. 1. Да, ошибочно представил новое поведение как существующее. Неизвестный TargetID оставить hard tick error: нарушена целостность состояния. Мёртвая цель → ActionFailed(TargetInvalid); мёртвый исполнитель → ActionFailed(ActorDead). Если мертвы оба — ActorDead. Silent fizzle заменить одним событием; эффект, recovery и RNG отсутствуют.

    1. Сохранить ascending EntityID во всех стадиях. InstanceID использовать только для адресации экземпляра и связи событий; нормативный порядок не менять.
      При одном действии на сущность это уже стабильный порядок экземпляров, воспроизводимый из состояния; сохраняется распределение RNG-бросков между исполнителями.

    2. canonicalVersion: 10 → 11, SimulationVersion: 10 → 11 без условия о числе бросков. Версия симуляции обозначает правила поведения, включая отмену, события и recovery, а не только RNG. Нулевой recovery сохраняет прежний тайминг при прочих равных, но не оправдывает сохранение версии 10. Совпадение потока существующего сценария нужно проверить. Golden — вручную согласованный файл testdata/traces/v11/minimal.golden.json плюс изменение embed-пути; без генератора и -update.

    3. Recovery и RecoveryRemaining — fixed.Fixed, Q16.16. Уменьшать тем же tempo-scaled шагом, что и windup, с ограничением снизу нулём. Tempo/haste влияет на recovery; изменение tempo применяется к последующим уменьшениям таймера.

    4. Повторно использовать EventActionPhaseChanged. Предлагаемый payload перехода: {Tick, EntityID, InstanceID, FromPhase: PhaseRecovery, ToPhase: PhaseNone}. Событие создать до очистки экземпляра, ровно один раз при завершении положительного recovery. Отдельный kind не добавлять.

    5. Источник — поле Action.Recovery, задаваемое при создании действия рядом с Windup. Для всех существующих действий и fixtures: 

      const DefaultActionRecovery fixed.Fixed = 0
      Отрицательное значение отклонять. При нуле после impact сразу завершать действие, без входа в PhaseRecovery и без события завершения recovery. Это временный балансный default; положительный recovery обязательно покрыть отдельным тестом.
