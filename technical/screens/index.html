    Как устроены экраны и общие правила интерфейса?¶

    Эта глава задаёт карту экранов MVP, общий контракт навигации, состояний, фокуса и входных view-model, по которому собирается каждый экран Godot.

    Реализует: основной цикл, изменения между узлами, полный доступ без мыши, поведение фокуса, увеличение интерфейса, чтение без цвета, экранный диктор.

    Какие экраны входят в MVP?¶

    MVP состоит из шестнадцати экранов. Эта карта владеет составом и допустимыми переходами; назначение, данные, команды и раскладка принадлежат главе конкретного экрана. Hub остаётся техническим именем маршрута, а во всех пользовательских текстах называется Дорожной кузней.

    Экран Назначение и основной вход
    Boot/Connection запускает клиентский путь подключения к локальному Go; открывается при старте приложения
    Main Menu выбирает профиль; открывается после успешного подключения
    Hub Дорожная кузня между забегами; открывается из Main Menu и после Run Result
    Inventory+Crafting показывает экипировку, рюкзак и верстак; открывается из Кузни и между комнатами
    AI Editor редактирует Мозг, его библиотеку и тесты; открывается из Кузни и между комнатами
    Progression показывает развитие, активные навыки и Память; открывается из Кузни и между комнатами
    Run Setup сводит выбранную подготовку перед стартом; открывается из Кузни
    Run Map выбирает следующий узел; открывается после Run Setup и завершения комнаты
    Combat Viewing воспроизводит готовую запись боя без вмешательства; открывается из боевого узла карты
    Room Resolution показывает итог комнаты и временную добычу; открывается после боя и из узла сокровища
    Rest обслуживает решение точки отдыха; открывается из соответствующего узла карты
    Shop обслуживает покупку и продажу за забеговое золото; открывается из узла лавки
    Run Result завершает забег после победы или смерти и ведёт обратно в Кузню
    Replay Library перечисляет сохранённые записи забегов; открывается из Кузни
    Replay Viewer разбирает запись с переходом по боям как по главам; открывается из библиотеки, итога комнаты или итога забега
    Settings/System Menu меняет локальную подачу и выполняет системные действия; открывается поверх любого экрана

    Основная последовательность проходит от Boot/Connection через Main Menu в Кузню, затем через Run Setup и Run Map к экрану выбранного узла. Бой ведёт в Room Resolution, смерть или завершение последнего акта — в Run Result, а результат забега возвращает в Кузню. Просмотр записи является ответвлением для анализа и всегда возвращает вызывающий экран; системное меню является слоем, а не новым местом в последовательности.

    Router в Godot владеет сменой сцен и историей возврата, но не решает, допустима ли механическая операция. Доступность маршрута выводится из подтверждённого view-model, а переход после gameplay-команды происходит только по принятому Go состоянию. Устройство router, StateBridge, command facade и ModalLayer принадлежит архитектуре клиента.

    Как работает постоянная панель вкладок?¶

    Вне полноэкранного просмотра действует один общий компонент с пятью вкладками: Мозг, Инвентарь, Прогрессия, Забег, Кузня. Панель не является экраном, не хранит gameplay-данные и не создаёт отдельную копию текущего профиля или забега. Переход между доступными занятиями выполняется одним действием и сохраняет локальный контекст экрана, с которого игрок ушёл.

    Вкладка Забег ведёт в Run Setup, пока забег не начат, и в Run Map, пока забег активен. Вкладка Кузня во время забега остаётся видимой и фокусируемой, объявляет недоступность и показывает локализованную причину; скрытие или один только приглушённый цвет нарушают контракт. Панель скрывается ровно на Boot/Connection, Main Menu, Combat Viewing и Replay Viewer, потому что эти экраны владеют всем кадром.

    Панель получает состояние только через selector текущего view-model и отправляет локальное намерение навигации router. Она не посылает gameplay-команду, не меняет server revision и не обходит входные условия целевого экрана. Если вызывающий объект после возврата существует, экран восстанавливает его выделение, прокрутку и фокус; подтверждённые данные при этом перечитываются из store.

    Кто владеет данными экрана?¶

    Go/симуляция владеет всеми фактами профиля, забега, Мозга, предметов, доступности операций и их revisions. StateBridge принимает эти данные, mapper строит типизированную клиентскую проекцию, а selector отдаёт экрану неизменяемый view-model для одного полного рендера. Экран владеет только представлением: маршрутом внутри сцены, фокусом, выделением, прокруткой, фильтрами, раскрытыми панелями и предварительными жестами.

    Каждый экран принимает один view-model через одинаковую границу независимо от источника. В S3 источником служит замороженная fixture из fixtures/ui/, в S9 — selector над live-проекцией; ветви if fixture, отдельной тестовой разметки и прямого обращения сцены к transport быть не должно. Формат fixture и её данные принадлежат направлению Go/симуляции, а Godot/клиент читает их без изменения.

    Выходы экрана разделены на локальные navigation intents и типизированные gameplay-команды через command facade. Локальное действие может открыть модальный слой, сменить вкладку или изменить presentation state. Механическая мутация остаётся предварительной до ответа Go; отказ сохраняет прежний подтверждённый view-model и даёт локализуемый код причины, а принятый ответ приносит новую revision.

    Какие состояния обязательны для экранов с данными?¶

    Экран с данными реализует четыре общих состояния. Скелет загрузки сохраняет будущую структуру, но не показывает выдуманные значения и не разрешает зависимые от них команды. Ошибка называет причину, предоставляет повтор и не маскируется бесконечным ожиданием. Устаревшая revision показывает, что отображение требует перечитывания, и не накладывает локальный diff на неизвестное состояние. Пустое состояние прямо называет следующее допустимое действие вместо пустой рамки.

    Экранная глава может доказать, что какое-либо состояние невозможно по доменному инварианту, но не может просто пропустить его. Дополнительные состояния успеха и недоступности описываются там, где они наблюдаемы: успех показывает подтверждённый исход, а недоступный элемент остаётся читаемым и сообщает причину, если само существование действия сохраняет смысл. Фатальная ошибка соединения принадлежит общему ModalLayer и перекрывает экран, не превращаясь в его локальное пустое состояние.

    Fixture-корпус содержит для каждого из шестнадцати экранов скелет загрузки, ошибку с повтором, устаревшую revision и пустое состояние. Даже экран, для которого доменная пустота невозможна, получает проверочный пример общего presentation contract либо явное доказательство неприменимости в своей главе. Fixture не является альтернативным источником игровых правил: она фиксирует форму входа и ожидаемое отображение.

    Как экран работает с модалями, фокусом и доступностью?¶

    Каждая сцена строится из Control и объявляет явный граф фокуса в том же порядке, в котором элементы расположены и читаются. Tab проходит между смысловыми областями, а большое полотно или сетка является одной внешней остановкой и организует пространственную навигацию внутри себя. Любое действие мышью имеет клавиатурный эквивалент; наведение не открывает сведений, которых нельзя получить выделением с клавиатуры.

    Модали создаются только через общий ModalLayer по контракту архитектуры клиента. Одновременно открыт не более чем один блокирующий слой. Он забирает фокус, полностью обслуживается клавиатурой и после закрытия возвращает фокус вызвавшему Control; если тот исчез, focus manager выбирает ближайшую допустимую цель в том же контексте. Escape сначала закрывает верхний закрываемый слой, затем внутренний детальный контекст и только после этого покидает экран или открывает системное меню.

    Router объявляет диктору локализованное имя нового экрана, а результат действия объявляется после подтверждённого успеха или отказа. Каждый интерактивный элемент передаёт имя, роль, значение и состояние; изменение, влияющее на следующий выбор, объявляется сразу. Цвет всегда дублируется формой, иконкой, текстом или силуэтом, видимый фокус не отключается темой, а проверка в оттенках серого остаётся обязательной.

    Раскладка поддерживает 16:9 и 21:9. Дополнительная ширина отдаётся конкретной рабочей области, указанной в главе экрана, а не растягивает все элементы одним коэффициентом. На каждом поддерживаемом шаге масштаба текст и controls не обрезаются и не накладываются; нехватка места решается контейнерами, переносом и прокруткой без исчезновения действия.

    По какому шаблону описывается отдельный экран?¶

    Каждая экранная глава сохраняет один порядок из пятнадцати частей, чтобы разработчик и агент находили один и тот же контракт в одном месте:

    1. назначение и один вопрос игрока;
    2. условия входа и входные guards;
    3. все пути выхода, включая Escape и отмену;
    4. входной view-model, локальное состояние и отправляемые команды;
    5. иерархия информации;
    6. раскладка 16:9 и 21:9;
    7. ввод, клавиатурный эквивалент и порядок фокуса;
    8. основной цикл взаимодействия;
    9. выделение, наведение, перетаскивание и модали;
    10. загрузка, пустота, stale revision, ошибки, успех и недоступность;
    11. визуальная и звуковая обратная связь;
    12. требуемые ассеты и граница их повторного использования;
    13. проверки доступности именно этого экрана;
    14. локально сохраняемый presentation state и точка возврата;
    15. наблюдаемые сценарии приёмки и зависимости от владельцев соседних контрактов.

    Глава не копирует поля Protobuf, opcode, ID, gameplay defaults или правила домена. Она связывает отображение с владельцем данных и называет поведение при отсутствии, отказе и несовместимости входа. Если для реализации требуется незакреплённый параметр, глава ссылается на соответствующую строку docs/open-questions.md и не ведёт собственный список.

    Как меняется контракт экрана?¶

    Форма обязательного view-model изменяется по схеме-first: направление Go/симуляции меняет владеющий application contract и замороженные fixtures, затем Godot/клиент обновляет mapper, selector и сцену. Fixture и live DTO обязаны снова приводить к одному view-model и одной разметке. Изменение темы, позиции или локального presentation state не повышает gameplay revision и не меняет wire-контракт.

    Неизвестная обязательная семантика не получает локальный default и не создаёт частично работающий экран. Mapper отвергает несовместимый вход по правилам контрактов и потока данных, а экран показывает предусмотренное состояние ошибки. Godot не переписывает fixture ради зелёного snapshot: смену её формы и содержимого выполняет владелец Go отдельным изменением до зависимого UI.
