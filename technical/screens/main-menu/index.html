    Как главное меню выбирает профиль и открывает игру?¶

    Эта глава задаёт контракт Main Menu: как Godot показывает доступные профили, создаёт новый профиль и передаёт выбранный профиль Дорожной кузне.

    Реализует: принадлежность персонажей и Мозгов профилю, одну Дорожную кузню на профиль, полный доступ без мыши, поведение фокуса, чтение интерфейса экранным диктором.

    Зачем существует экран и на какой вопрос отвечает?¶

    Main Menu отвечает на один вопрос: «С каким профилем войти в игру?» Экран перечисляет профили, позволяет выбрать существующий или создать новый и после ответа Go открывает Hub, который в пользовательском тексте называется Дорожной кузней. Выбор персонажа, назначение Мозга, чтение прогресса и запуск забега начинаются уже в Кузне.

    Профиль является верхней игровой границей: ему принадлежат общая Кузня, несколько персонажей, библиотека Мозгов, сундук и постоянные открытия. Главное меню не разворачивает эти агрегаты в карточки и не превращается во вторую Кузню. Строка списка должна позволять однозначно выбрать профиль, но состав её transport- или storage-полей определяется application contract владельца Go, а не сценой.

    Когда экран открывается?¶

    Router открывает Main Menu после единственного успешного перехода из Boot/Connection. К этому моменту compatibility gate завершён, StateBridge готов принимать игровую проекцию, а transport credentials уже скрыты bootstrap adapter. Экран не повторяет handshake и не показывает endpoint, token, protocol fields или content hash.

    Второй вход приходит из Settings/System Menu, когда игрок явно возвращается в главное меню. Такой переход уничтожает прежний route context и заново запрашивает список профилей. Панель постоянных вкладок здесь скрыта по общей карте экранов, потому что профиль ещё не выбран для текущего входа в игру.

    Куда ведёт экран?¶

    Выбор существующей строки отправляет намерение открыть этот профиль. Переход в Hub происходит только после ответа Go и публикации пригодной проекции; нажатие не меняет route оптимистично. Новый профиль создаётся отдельной командой, после чего экран использует тот же путь открытия и не строит локальную заготовку профиля.

    Если полная загрузка выбранного профиля выявляет невалидное сохранение, главное меню не показывает частично прочитанные данные и не предлагает собственную починку. Router передаёт пользователя в предусмотренное состояние Hub, где находятся диагностика, восстановление из полностью проверенного backup и явное создание нового профиля по контракту persistence. Главное меню не дублирует эти три действия.

    Кнопка настроек открывает общий Settings/System Menu поверх текущей сцены, а Escape делает то же, если более приоритетного слоя нет. Выход из приложения проходит через lifecycle request и согласованное завершение по топологии runtime. Screen script не вызывает немедленное завершение процесса и не оставляет Go core без дочернего клиента.

    Кто владеет входами и выходами?¶

    Go/симуляция владеет каталогом профилей, стабильной идентичностью каждой записи, результатом создания и открытия, revision списка и полной валидностью загружаемого агрегата. Persistence хранит данные и выполняет проверку, а application layer выдаёт безопасный для списка view-model. Main Menu не читает SQLite, не открывает save-файлы и не выводит внутренние storage paths.

    Godot/клиент владеет выделенной строкой, прокруткой, фокусом, состоянием ожидания команды и маршрутом к системному меню. Selector получает неизменяемый view-model через StateBridge; fixture на S3 и live DTO на S9 приводятся к одной форме и рисуются одной сценой. Прямая зависимость от transport, ветвь if fixture и локальный gameplay-cache запрещены общим контрактом клиента.

    Экран выпускает две gameplay-команды: создать профиль и открыть выбранный профиль. Он также выпускает локальное намерение открыть системное меню и lifecycle request на выход. Переименование, удаление, импорт, экспорт, выбор персонажа и выбор Мозга в контракт экрана не входят; отсутствие источника для такой операции не восполняется новой кнопкой.

    Команда открытия использует стабильную идентичность строки, а не её видимый текст или позицию в списке. Пока ответ ожидается, повторная отправка того же действия блокируется на уровне presentation state. Отказ возвращает строку в доступное состояние, сохраняет прежнюю проекцию и сообщает машинно-различимую причину через локализованный текст.

    Что игрок читает первым?¶

    Первым читается название игры, затем список профилей, после него действие создания нового профиля и системные действия. Версия сборки располагается отдельно внизу и не конкурирует со списком. Подзаголовок и декоративный фон поддерживают образ игры, но не входят в граф фокуса и не получают приоритет перед выбором.

    Строка профиля сообщает доступное имя и состояние выбора, достаточные для однозначного открытия. Она не перечисляет персонажей, Мозги, предметы, результаты забега или показатели прогресса: эти сведения принадлежат Кузне и её дочерним экранам. Ошибка конкретного открытия показывается рядом с выбранной строкой или в общем модальном слое, но не превращает остальные профили в недоступные без причины от Go.

    Как устроена раскладка на 16:9 и 21:9?¶

    Экран использует полноэкранный фон и центральную вертикальную колонку. В колонке сверху вниз находятся знак и название игры, список профилей, создание профиля, вход в настройки и выход. Версия сборки закреплена у нижнего края композиции; она берётся из build metadata и форматируется для показа без захардкоженного player-visible шаблона в scene resource.

    Список получает ограниченную высоту и собственную вертикальную прокрутку, поэтому рост числа профилей не выталкивает системные действия за границу кадра. На 21:9 колонка не растягивается во всю ширину: дополнительное место получает фон. При каждом поддерживаемом масштабе текст переносится, controls сохраняют минимальную область взаимодействия, а горизонтальная прокрутка не требуется.

    Как работают ввод и фокус?¶

    Порядок фокуса фиксирован: список профилей → создание профиля → настройки → выход. Внутри списка стрелки меняют выделение, Enter открывает выбранную строку, а Tab покидает список в сторону следующей смысловой области. Декоративные заголовки, фон, музыка и версия сборки не являются остановками фокуса.

    Первую доступную строку можно сфокусировать сразу после загрузки списка. Если список пуст, фокус переходит на создание профиля; при ошибке чтения — на повтор. После закрытия системного меню focus manager возвращает фокус вызвавшей кнопке, а после отмены подтверждения выхода — на действие выхода.

    Мышь выбирает ту же строку и вызывает те же команды, что клавиатура. Наведение не раскрывает дополнительных данных, двойной клик не обходит ожидание ответа Go, перетаскивания нет. Все действия проходят через переназначаемые Godot actions, а не через проверку конкретных keycodes внутри main_menu.gd.

    Как выглядит основной цикл взаимодействия?¶

    Штатный цикл короток: прочитать список, выбрать профиль, дождаться ответа и войти в его Кузню. Для первого запуска цикл начинается с явного пустого состояния: создать профиль, получить его от Go и открыть тем же маршрутом. Главное меню не добавляет промежуточный экран character_profile, потому что этот компонент слит с Кузней по карте экранов MVP.

    Смена профиля выполняется только возвратом в Main Menu через системное меню. Экран не держит две одновременно активные проекции и не переносит выбранного персонажа, Мозг или локальный draft между профилями. После входа Кузня читает принадлежавшие выбранному профилю данные из новой проекции.

    Как ведут себя выделение и модальные слои?¶

    Выделяется одна строка профиля. Визуальное выделение, клавиатурный фокус и объявляемое диктором состояние различимы между собой, чтобы перемещение фокуса не выглядело как уже выполненный выбор. До ответа Go строка показывает ожидание, но прежний профиль не считается открытым локально.

    Создание профиля не открывает отдельный экран и не требует полей, которых нет в application contract. Ошибка создания или открытия отображается через общий ModalLayer либо область ошибки списка с повтором. Системное меню и подтверждение выхода также создаются общим ModalLayer; одновременно существует не более одного блокирующего слоя, и после его закрытия фокус возвращается к источнику.

    Какие состояния обязан различать экран?¶

    Загрузка. Центральная колонка и будущая область списка остаются на месте, но строки не содержат выдуманных имён, а создание и открытие недоступны до получения view-model. Скелет не подменяет ошибку бесконечной анимацией.

    Пусто. Список явно сообщает, что профилей нет, и называет следующее действие — создать профиль. Действие доступно с клавиатуры и получает первый фокус. Пустая рамка, неактивная кнопка «играть» или автоматическое создание профиля нарушают контракт.

    Устаревшая revision. Если Go сообщает более новую revision каталога, экран показывает необходимость обновления и перечитывает список. Он не сохраняет локально исчезнувшую строку и не накладывает прежнее выделение на другую стабильную идентичность. Если выделенный профиль после обновления отсутствует, focus manager выбирает ближайшую существующую строку либо создание профиля.

    Ошибка чтения. Экран показывает честную локализованную причину и действие повтора. Уже полученные строки не выдаются за актуальный список, а ошибка transport не превращается в пустоту. Фатальный разрыв связи принадлежит верхнему уровню ModalLayer и запрещает новые gameplay-команды.

    Ошибка команды. Отказ создания или открытия сохраняет текущий список, снимает ожидание только с вызвавшего действия и объявляет причину. Невалидное сохранение не обрабатывается как обычный локальный retry и не получает частичный профиль; пользовательский flow его восстановления принадлежит Hub.

    Успех. После принятого создания список получает новую проекцию. После принятого открытия router один раз переходит в Hub; повторный outcome той же команды не создаёт вторую сцену и не дублирует загрузку.

    Недоступность. Строка или действие остаются фокусируемыми и называют причину, если Go сохраняет их в каталоге, но временно запрещает открытие. Если операция вообще не входит в MVP, соответствующего control на экране нет.

    Какая обратная связь нужна экрану?¶

    Появление списка, начало открытия, принятый вход и отказ получают различимые UI-события. Выбор конкретных streams, buses, приоритетов и правила menu music принадлежат audio runtime; экран только выпускает семантические UI intents. Звук никогда не является единственным признаком открытого, ожидающего или ошибочного состояния.

    Короткое появление центральной колонки допустимо, но не задерживает доступ к профилям и отключается настройкой снижения движения. Анимация не проигрывается заново при каждой revision списка и не сбрасывает фокус. Переход в Кузню начинается сразу после принятого результата, а не после завершения декоративного fade.

    Какие ассеты требуются?¶

    Экран переиспользует общую тёмную тему, шрифты, focus style, оформление списка, ошибки и модали. Требуются знак или текстовое название CodeDungeon, подзаголовок, полноэкранный фон и компактное оформление версии сборки. Отдельная трёхмерная сцена, портреты персонажей, изображения Мозгов и декорации Кузни этому экрану не принадлежат.

    Существующая menu music подключается через каталог audio runtime, а не прямой путь из screen script. Производство, provenance и импорт изображений и шрифтов принадлежат asset pipeline. Все видимые названия, подзаголовок, действия, состояния и причины находятся в codedungeon/translations/translations.csv и вызываются через tr(); scene resource и GDScript не содержат пользовательских строк.

    Как проверяется доступность?¶

    Диктор объявляет имя экрана, число доступных профилей и затем каждую строку как выбираемый элемент с именем и состоянием. При пустоте он сразу называет создание профиля, при ошибке читает причину до действия повтора, а при ожидании и результате не повторяет объявление на каждый transport event. Версия и декоративный подзаголовок не перебивают основной список.

    Весь путь — выбор, создание, повтор чтения, открытие настроек и отмена выхода — проходится без мыши. Видимый focus style различает фокус и выбранную строку, а снимок в оттенках серого сохраняет loading, error, selected и disabled states. Снимки на 16:9, 21:9, максимальном поддерживаемом масштабе и для ru и en сохраняют список, системные действия и тексты без обрезки и наложения.

    Что экран сохраняет между визитами?¶

    Пока сцена существует, локальный presentation state хранит выделенную строку, прокрутку и focus return token. Эти значения не входят в profile save, gameplay revision или settings file и не выбирают профиль после пересоздания сцены. После возврата из системного меню экран восстанавливает фокус, но актуальность списка по-прежнему определяет selector.

    Принятый профиль хранится только в авторитетной проекции Go. После перехода Main Menu освобождает список и локальное ожидание команды; Кузня не читает данные из оставшейся сцены. При явном возврате в главное меню selector заново строит каталог и не использует сохранённую копию списка.

    Какие сценарии фиксируют контракт?¶

    Успешный путь из Boot/Connection загружает список один раз, открывает выбранный профиль только после ответа Go и приводит в одну принадлежащую ему Кузню. Создание из пустого состояния формирует профиль через Go, обновляет список и использует тот же маршрут входа. Повторный command outcome и двойной клик не создают дубликат профиля и не выполняют второй переход.

    Loading, empty, stale revision, read error, command error и success fixtures строят одну разметку. Ошибка чтения предоставляет повтор, stale revision перечитывает список без подмены идентичности, а невалидное сохранение не загружается частично и передаётся пользовательскому flow Кузни. Возврат из системного меню и отмена выхода восстанавливают правильный фокус.

    Экран не показывает постоянную панель вкладок, персонажей, Мозги, инвентарь, прогресс или команды забега. Полный сценарий выполняется клавиатурой и диктором; снимки layout, localization и grayscale проходят; ни одна player-visible строка не остаётся в .tscn или .gd.
