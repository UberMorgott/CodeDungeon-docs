    Как клиент показывает запуск и подключение к локальному Go?¶

    Эта глава задаёт первый экран Godot: какие состояния локального запуска он показывает, когда пропускает игрока дальше и как ведёт себя при отказе соединения.

    Реализует: полный доступ без мыши, чтение интерфейса экранным диктором.

    Зачем существует экран и на какой вопрос отвечает?¶

    Boot/Connection отвечает на один вопрос: «Готова ли локальная игра к выбору профиля?» Он показывает запуск presentation-runtime, установление связи с авторитетным Go core и конечный исход проверки совместимости. Игрового выбора, профиля, Мозга, Памяти или состояния забега на этом экране нет.

    Экран не запускает Godot-процесс. Точкой входа является Go launcher/core, который подготавливает локальные зависимости и создаёт единственный дочерний Godot по контракту топологии runtime. Boot/Connection является первой сценой уже запущенного клиента и представляет состояние bootstrap adapter, не присваивая себе lifecycle процессов.

    Когда экран открывается?¶

    Router открывает Boot/Connection первым экраном каждого нового Godot-процесса. Панель постоянных вкладок скрыта; профиль ещё не выбран, а StateBridge ещё не предоставляет экранам игровую проекцию. Повторный запуск дочернего процесса снова начинает с этой сцены и не восстанавливает её локальное presentation state.

    Входным условием служит launch context текущего поколения runtime. Endpoint и token потребляет только bootstrap/transport adapter: screen scene не читает, не отображает и не логирует эти значения. Если launch context отсутствует или непригоден, сцена переходит в явную ошибку и не пытается подобрать endpoint, фиксированный порт или token.

    Ошибка, возникшая до создания дочернего Godot, на этом экране не появляется по построению. Если Go не открыл content package или SQLite, не создал loopback listener либо не смог запустить и прикрепить клиента к process-management adapter, launcher завершает запуск со своей диагностикой. Глава не обещает UI там, где ещё нет окна.

    Куда ведёт экран?¶

    Успешная readiness-проверка ведёт только в Main Menu. Router выполняет переход один раз после lifecycle-события ready; кнопки «продолжить» нет, потому что игрок не подтверждает совместимость вручную. Main Menu получает данные профилей уже через обычную клиентскую проекцию и не повторяет bootstrap.

    При retryable-ошибке команда повтора остаётся на этом экране и просит bootstrap adapter начать новую попытку подключения. Она не является gameplay-командой, не получает доменный outcome и не создаёт параллельное соединение: текущая попытка сначала переводится в завершённое состояние. Endpoint и token экран при повторе не генерирует; новым поколением credentials и перезапуском дочернего процесса владеет Go launcher.

    Escape открывает общий Settings/System Menu поверх сцены, когда нет более приоритетного слоя. Из него доступны локальные настройки и согласованный выход; закрытие возвращает фокус на прежний элемент Boot/Connection. Закрытие окна также начинает graceful shutdown по контракту runtime, а не оставляет core работать без клиента.

    Какие данные и события проходят через экран?¶

    Фактическим состоянием запуска владеет Go launcher/core: живостью дочернего процесса, listener, текущими credentials, readiness, heartbeat и причиной lifecycle-отказа. Godot bootstrap adapter превращает только безопасную для показа часть этого состояния в локальный view-model. Screen scene читает его через selector StateBridge, как и остальные сцены, и не обращается к WebSocket напрямую.

    Входной view-model сообщает текущую фазу показа, факт ожидания или завершения попытки, локализуемый machine-readable код отказа, допустимость повтора и безопасный diagnostic identifier. Имена wire-сообщений и поля сюда не копируются. Точный порядок negotiation остаётся зависимостью от записи «Как устроено рукопожатие между Godot и побочным процессом ядра?»; до её закрытия экран отображает состояния adapter и не закрепляет собственную последовательность handshake.

    Форма обязательного lifecycle view-model меняется schema-first: владелец Go/симуляции сначала обновляет fixture и источник состояния, затем Godot/клиент обновляет adapter, selector и сцену. Неизвестная обязательная фаза или причина не получает локальный default и переводит экран в диагностируемую ошибку. Версии wire-контракта при этом остаются у контрактов и потока данных, а screen scene не ветвится по protocol_version.

    Экран выпускает только локальные UI intents: повторить подключение, открыть системное меню и запросить выход. Событие готовности приходит от adapter и передаётся router; пользователь не может выпустить его кнопкой. Gameplay-команды запрещены до readiness, а screen script не создаёт профиль, сессию, snapshot или локальную замену авторитетного состояния.

    Что игрок читает первым?¶

    Первым читается итоговое состояние: запуск продолжается, соединение готово либо запуск остановлен. Вторым идёт краткое описание текущего шага без процентов и оценок времени: источники задают конечный deadline, но не задают числовую шкалу прогресса. Третьим при отказе показываются причина, diagnostic identifier и доступное следующее действие.

    Технические значения endpoint, token, protocol_version, content_hash, sequence и содержимое envelope не выводятся. При несовместимости игрок получает понятную локализованную категорию и безопасную диагностику, а подробности для разработчика остаются в локальных логах. Экран не превращает bootstrap в панель сетевой отладки.

    Как устроена раскладка на 16:9 и 21:9?¶

    Композиция состоит из полноэкранного фона и компактной центральной колонки. В ней сверху вниз расположены общий знак игры, название текущего шага, индикатор неопределённого ожидания, область ошибки и доступные действия. Будущая структура сохраняется при загрузке, поэтому переход к ошибке не сдвигает фокус и не перестраивает весь экран.

    На 21:9 центральная колонка не растягивается и не разносит статус с действием по краям. Дополнительная ширина уходит фону; она не добавляет сведения и не меняет порядок чтения. На каждом поддерживаемом масштабе текст переносится внутри колонки, а действия остаются видимыми без уменьшения шрифта и без горизонтальной прокрутки.

    Как работают ввод и фокус?¶

    Во время нормального ожидания интерактивных элементов нет, поэтому фокус не помещается на декоративный индикатор. При ошибке первым получает фокус «повторить», если повтор допустим; затем идёт вход в системное меню. Постоянный отказ оставляет доступным системное меню и выход, а причина невозможности повтора объявляется текстом и состоянием элемента, не одним цветом.

    Все действия выполняются с клавиатуры. Видимый индикатор фокуса сохраняется во всех темах, Tab следует визуальному порядку, Enter активирует выбранное действие, а Escape подчиняется общему модальному порядку. Мышь не открывает дополнительных сведений и не является единственным способом повторить попытку или завершить приложение.

    Каков основной цикл взаимодействия?¶

    В штатном случае игрок ничего не делает: видит короткий ход запуска и автоматически попадает в Main Menu. При временном отказе цикл выглядит так: прочитать причину, запустить повтор, увидеть новую попытку и дождаться readiness либо нового конечного исхода. Повтор не скрывает прежний отказ до начала новой попытки и не сбрасывает diagnostic identifier, пока он нужен для обращения к логам.

    Экран не разрешает бесконечное молчаливое ожидание. Каждый bootstrap attempt заканчивается готовностью или явным отказом по конечному lifecycle deadline, числовое значение которого принадлежит runtime-конфигурации. Анимация не подменяет этот переход и не продолжает вращаться после зафиксированной ошибки.

    Как работают выделение, наведение и модальные слои?¶

    Выделяемыми бывают только доступные действия ошибки. Наведение повторяет имя, состояние и пояснение, доступные при клавиатурном фокусе; перетаскивания на экране нет. Индикатор запуска, знак игры и фон исключены из графа фокуса и дерева действий диктора, если не несут отдельного текста.

    Ошибка подключения использует самый высокий уровень общего ModalLayer, предназначенный для фатальной ошибки и разрыва связи. Сцена не создаёт вторую модалку поверх него и не вкладывает подтверждения. После retry слой закрывается только при принятом запросе новой попытки; если запрос не принят, причина остаётся видимой и фокус возвращается на действие повтора.

    Какие состояния обязан различать экран?¶

    Загрузка. Показываются знак игры, индикатор неопределённого ожидания и текст текущей lifecycle-фазы. Выдуманных процентов, оставшегося времени, данных профиля и активных вкладок нет. Смена фазы объявляется диктором только когда меняет понимание следующего шага, чтобы не создавать поток повторяющихся сообщений.

    Пусто. Доменная пустота неприменима: экран не отображает коллекцию. Отсутствующий launch context, отсутствие listener status или пустой обязательный код состояния являются ошибкой входа, а не приглашением создать данные. Fixture доказывает это явным состоянием ошибки вместо пустой рамки.

    Устаревшая revision. Gameplay revision до readiness не существует. Событие закрытого соединения или предыдущего поколения runtime не может перевести текущую сцену в ready; adapter отбрасывает его и сохраняет текущий исход. Проверочная fixture доказывает отсутствие перехода по устаревшему событию.

    Ошибка. Экран различает безопасными локализуемыми причинами отсутствие пригодного launch context, невозможность соединиться до deadline, отказ token, несовместимость protocol, несовпадение content hash и потерю core во время bootstrap. Ошибка не создаёт частичную проекцию и не открывает Main Menu. Повтор показывается только когда adapter допускает его; несовместимость и отказ credentials остаются конечным исходом текущего поколения.

    Успех. Authentication и compatibility gate завершены, а lifecycle adapter выпустил ready. Router меняет сцену ровно один раз; позднее повторение того же события не создаёт второй Main Menu и не дублирует загрузку профилей.

    Недоступность. Gameplay-навигация и команды отсутствуют целиком до успеха. Если повтор недоступен, элемент остаётся читаемым и называет причину, пока системное меню и выход сохраняют путь из экрана.

    Какая обратная связь нужна?¶

    Переход между ожиданием, готовностью и отказом получает короткий UI cue, но звук не является единственным носителем состояния. Выбор конкретного AudioStream, bus, приоритета и поведения при недоступном audio device принадлежит audio runtime. Готовность не задерживается ради анимации или звука: router может сменить сцену сразу после события.

    Индикатор ожидания отражает только неопределённую работу и прекращает анимацию при конечном исходе. Настройка снижения движения заменяет его статическим различимым состоянием. Вспышки, пульсация и повторяющиеся звуки не используются для сообщения о длительном ожидании.

    Какие ассеты нужны?¶

    Экран переиспользует общую тему, шрифты, focus style, оформление ошибок и знак игры. Собственной трёхмерной сцены, отдельного сетевого набора иконок или уникального фона он не требует. Производство, provenance и импорт общих ресурсов принадлежат asset pipeline, а экран только перечисляет потребителей.

    Все player-visible названия фаз, причины, действия и объявления находятся в codedungeon/translations/translations.csv и вызываются через tr(). Machine-readable причины не показываются как английские enum и не собираются конкатенацией. Отсутствующий translation key является дефектом сборки, а не поводом молча вывести transport code.

    Как проверяется доступность?¶

    Диктор объявляет имя экрана при входе, затем текущий исход и следующее доступное действие. При ошибке он читает причину до кнопки повтора и не озвучивает token, endpoint или декоративное описание заставки. Смена на ready объявляется один раз перед переходом, а повторяющиеся heartbeat или transport-события не создают речевой шум.

    Полный ошибочный путь проходится только с клавиатуры: открыть системное меню, вернуться, запустить допустимый повтор и завершить приложение. Снимки на 16:9, 21:9, максимальном поддерживаемом масштабе, для ru и en, при снижении движения и в оттенках серого сохраняют статус, причину, фокус и все доступные действия.

    Что экран сохраняет между попытками?¶

    Экран не сохраняет gameplay-данные, transport credentials, число попыток или последний отказ между запусками клиента. Новое поколение runtime начинает с нового view-model, а старые endpoint и token не попадают в settings store, save, replay или fixture. Локальная фаза и diagnostic identifier живут только до перехода, завершения процесса или начала новой попытки.

    Открытие системного меню временно сохраняет текущий screen state и focus return token. После закрытия меню фокус возвращается на вызвавший элемент; переход в Main Menu освобождает bootstrap state. Пользовательские настройки, изменённые в системном меню, сохраняются своим store и не становятся состоянием Boot/Connection.

    Какие сценарии фиксируют контракт?¶

    Успешный запуск показывает конечную последовательность lifecycle-состояний и ровно один раз открывает Main Menu; до ready ни одна gameplay-команда не уходит. Неверный token, несовместимый protocol и другой content hash дают разные локализованные отказы, не создают проекцию и не открывают следующий экран. Временный transport-отказ предоставляет один управляемый с клавиатуры повтор без параллельного соединения.

    Два последовательных запуска не показывают и не сохраняют credentials друг друга. Устаревшее событие закрытой попытки не переводит новую в ready; закрытие окна начинает graceful shutdown; потеря Go не оставляет экран в бесконечном ожидании. Fixture и live lifecycle adapter строят одну разметку, а все accessibility и layout snapshots проходят без отдельной тестовой сцены.
