    How does arena model v10 define an encounter?¶

    This chapter is the normative implementation specification for the v10 replacement of the shipped v9 arena model.

    Implements: authoritative combat geometry, deterministic simulation, and arena presentation.

    Normative words MUST, MUST NOT, SHALL, and REJECT are requirements. “Reject” means a typed error before tick 0 and no completed combat record. This document specifies simulation behavior, not Go type names.

    1. What is in scope and already fixed?¶

    1. One encounter uses one standalone rectangular arena. Its bounded interior is walkable by default; the camera pans across it. A run still contains many arenas on the global-map path, and there are no linked rooms inside one arena.
    2. The v10 default boundary is (0, 0, 60 * fixed.ONE, 40 * fixed.ONE), or 60 m × 40 m, and its default spawn lattice step is 1 * fixed.ONE. The metre-to-screen assumption is 24 m × 13.5 m visible at once in the 1280 × 720 viewport, an exact common scale of 160/3 px/m. The default arena is therefore 2.5 screen widths by 80/27 (about 2.96) screen heights. The viewport and stretch settings are current project facts (codedungeon/project.godot:23-30).
    3. Zones do not exist in v10. There are no zone records, zone membership, zone centres, Poisson-disk zone placement, Delaunay edges, passages, portals, or zone-keyed spawn candidates.
    4. The rectangle edge is impassable. Boundary is its only gameplay representation. Biome perimeter dressing is client-only.
    5. In-bounds void is gameplay geometry. A unit whose centre enters void falls and dies in the same tick. Hazard patches are walkable quicksand: their tempo slow ramps with sampled dwell time.
    6. Go owns every authoritative coordinate, region, route, derived spawn, terrain dwell, fall, and death. The Godot grid and Wang tiles are one-way presentation derivations.

    The shipped collision state is already a boundary plus filtered contacts (server/internal/sim/arena.go:93-101), and its body-radius inset defines the legal centre rectangle (server/internal/sim/arena.go:178-207). The v9 layout is a separate zone/portal structure (server/internal/sim/arena_layout.go:46-88), and its connectivity check proves only portal-graph connectivity (server/internal/sim/arena_layout.go:270-287). Production initialization accepts positioned entities through Input and retains the resolved arena (server/internal/sim/run.go:5-16,36-41; server/internal/sim/state.go:45-100; server/internal/sim/types.go:105-124). These are current-code facts, not v10 requirements.

    2. What is the numeric contract?¶

    • Every simulation distance, coordinate, speed, radius, clearance, and tempo rate is signed Q16.16 in fixed.Fixed; fixed.ONE == 65536. Ticks, counts, enum values, costs, weights, dwell counters, and stable IDs are integers. The existing contract uses signed int32 storage, int64 intermediates, no float, and truncation toward zero (simulation numeric model).
    • No v10 simulation code may use float32, float64, a float literal, epsilon, or conversion through float.
    • Q16.16 arithmetic and narrowing use internal/fixed. A checked operation reporting saturation rejects the arena or run. In particular, tempo scaling uses MulChecked; Mul discards that saturation flag (server/internal/fixed/fixed.go:144-154).
    • Squared distances use exact non-negative integers. Validation requires the boundary's integer diagonal weight, floor(sqrt(span_x^2+span_y^2)), to be at most 2^31-1 raw units. Therefore every in-arena axis difference used by the section 5.3 gap, section 6.1 edge length, and section 7.1 clearance is at most 2^31-1; each square is less than 2^62 and their sum is less than 2^63, which fits uint64. Form signed differences in int64, take their non-negative magnitudes, then convert to uint64 before multiplying. The diagonal bound also guarantees that an edge weight narrowed through FromRaw64Checked is representable. A positive Q16.16 gap is at most 2^31-1, so its square also fits. Generator predicates outside those bounds may use math/big.Int. Integer square roots use the existing overflow-reporting squared-length pattern and integerSquareRoot (server/internal/fixed/fixed.go:26-34; server/internal/sim/collision.go:194-221).
    • Unless stated otherwise, signed division truncates toward zero. For non-negative values, ceil(n/d) is n/d plus one iff n%d != 0; (n+d-1)/d is forbidden.
    • One raw unit is 1/65536 m.

    3. What is the canonical arena model?¶

    3.1 What do producers provide?¶

    ArenaSpec and ArenaLayout are replaced by one producer input, ArenaDefinition, and one immutable canonical result, ArenaArtifactV10. Procedural and authored producers pass through the same canonicalization and validation.

    ArenaDefinition
    Boundary                 AABB
    MaxSupportedBodyRadius   fixed.Fixed
    SpawnLatticeStep         fixed.Fixed
    SpawnClearance           fixed.Fixed
    HeroSpawnCapacity        uint32
    EnemySpawnCapacity       uint32
    Objects                  []ArenaObjectDefinition

    SpawnSites is deliberately absent from producer input, the artifact, and canonical artifact bytes. Sites are a deterministic derived view of the fields above. There is no spawn-site digest: the artifact digest already commits every input from which the complete site set is derived.

    The artifact contains the canonicalized fields above. Producer kind, generation seed, source filename, and provenance do not enter it. Object ID is the canonical object index plus one and is not stored again. The shipped Input and state carry the seed and encounter ID at this seam (server/internal/sim/run.go:5-16; server/internal/sim/state.go:11-22; server/internal/sim/canonical.go:48-57); v10 adds no generation-attempt or retry index.

    3.2 How are the boundary, participants, and anchors constrained?¶

    • Boundary is the inclusive Q16.16 AABB (min_x, min_y, max_x, max_y), with positive spans and integer diagonal weight floor(sqrt(span_x^2+span_y^2)) <= 2^31-1 raw units. The simulation does not require either span to be a multiple of a presentation cell.
    • MaxSupportedBodyRadius > 0, SpawnLatticeStep > 0, and SpawnClearance >= 0.
    • V10 initial encounters require HeroSpawnCapacity == 1 and 1 <= EnemySpawnCapacity <= 5. This matches the existing one-hero and five-enemy ceiling (encounter composition). Resolution MUST validate every initial participant has 0 < BodyRadius <= MaxSupportedBodyRadius; otherwise it rejects before tick 0. Body radius is immutable authoritative entity state (server/internal/sim/types.go:105-119). There is no reinforcement-pool input: the shipped encounter input contains only seed, encounter ID, arena, and initial entities (server/internal/sim/run.go:5-16).
    • For radius r, legal centres occupy the inclusive rectangle [min_x+r, max_x-r] × [min_y+r, max_y-r]. An empty interval rejects. Touching the perimeter is legal.
    • Stored AABBs have positive area. Gameplay AABB membership is inclusive.
    • At most 30 initially active Solid plus Void footprints are allowed in one v10 artifact. This is the navigation-density bound used by sections 5.1 and 6.2; inactive catalogue entries and hazards do not count until a future mutation rule activates them.
    • The gameplay object count must not exceed 0x7fffffff, so every derived terrain status ID is representable and unique.

    V10 has no RequiredClearance record. An earlier draft of this chapter carried one as a validation anchor; nothing was ever built against it, and the guarantees it was meant to give are already delivered by other rules that shipped: the single maximum-radius free-space component of section 6.1, the local site predicate of section 7.1, and the spawn-witness reserve that makes assignment total. An anchor list would be a second, weaker statement of the same thing, and every producer would have to author it. If a future version needs an authored anchor, it arrives with its own bytes and its own version.

    3.3 Which gameplay objects exist?¶

    ArenaObjectDefinition
    ContentID        (namespace UTF-8 bytes, uint32 value)
    Footprint        AABB
    Kind             Solid | Hazard | Void
    InitiallyActive  bool
    RampLossPerTick  fixed.Fixed
    • Solid blocks circle bodies and line-of-fire. RampLossPerTick == 0.
    • Void does not depenetrate a body; inclusive centre entry causes a fall. RampLossPerTick == 0.
    • Hazard is walkable quicksand. It requires 1 <= RampLossPerTick.Raw() <= 49152; section 9 defines dwell and rate.

    All footprints lie inside Boundary. Solid-solid, void-void, and solid-void contact or overlap are legal. This deliberately permits long walls assembled from pieces, L-corners, dense rubble, repeated boxes, and cliff walls touching or overhanging a chasm. Hazard footprints may overlap any role; effects in unwalkable overlap are simply unreachable.

    There is no simulation Decoration kind. Grass, decals, scatter, and decorative dunes are client-owned assets and consume neither object IDs nor canonical bytes. If a future decoration becomes targetable or destructible, that new gameplay kind requires a new simulation version. The current asset catalogue already has client decoration entries (codedungeon/assets/arena/arena_asset_contract_v1.json:368-399).

    3.4 What is stored and what is derived?¶

    Stored in the immutable artifact: boundary, maximum radius, spawn parameters and capacities, the complete ordered gameplay object catalogue, initial activity, and ramp payloads. That list is exactly the canonical artifact bytes of section 11, so the digest commits every stored field and nothing else: two arenas that differ only in a spawn parameter are two different arenas with two different digests, and a derived cache built under one of them cannot be attached to the other.

    Stored in per-tick canonical state: the 32-byte artifact digest, entities, ordinary and terrain statuses, action progress, events, RNG states, and other mutable encounter fields. When destruction ships, add only an activity/durability vector keyed by permanent object ID.

    Derived and non-canonical: the final spawn-witness reserve, spawn sites, collision contacts, forbidden unions, spatial indexes, graph nodes and edges, path-query results, per-site clearance/connectors, hazard membership, presentation cells, and Wang signatures. These views form one ArenaDerivedCache, keyed by the 32-byte artifact digest. A cache can be rebuilt without changing bytes, hashes, events, or RNG.

    Procedural generation MUST return a resolved bundle (artifact bytes, artifact digest, ArenaDerivedCache) from its completed construction, and the caller MUST hand that same bundle to Run; a digest/key mismatch rejects. Run MUST NOT repeat graph or site construction on a matching cache. Authored preset load and snapshot restore are the only v10 paths that rebuild the cache, after decoding and validating artifact bytes and verifying their digest. This replaces the shipped seam where Run calls newState, newState resolves the artifact again, and only its collision arena survives (server/internal/sim/run.go:30-42; server/internal/sim/state.go:40-63,94-100). Current restore decodes canonical bytes into a fresh state (server/internal/sim/snapshot.go:21-33; server/internal/sim/canonical.go:252-272), so the recovery capsule specified in section 11 supplies the immutable artifact bytes needed for that rebuild.

    The current loop hashes canonical state after every tick (server/internal/sim/run.go:52-62), and the hash is SHA-256 over the full canonical buffer (server/internal/sim/canonical.go:48-57,136-139). V10 therefore computes the artifact digest once during resolution and appends only those cached 32 bytes to each canonical state.

    4. How are objects ordered and mutated?¶

    Canonical object order is:

    1. signed raw (min_x, min_y, max_x, max_y);
    2. exact canonical content ID bytes <namespace>:<uint32>.

    The shipped comparator and resolver establish that ordering and assign the full-set index (server/internal/sim/arena.go:50-61,113-136; server/internal/sim/arena_layout.go:104-130). Kind, activity, and ramp are not tie-breakers; an identical full key rejects. Equal AABBs with distinct content IDs remain legal, so the existing equal-AABB contact merge is meaningful (server/internal/sim/arena_layout.go:123-130).

    Filtering never renumbers objects. Future destruction or deactivation changes the mutable vector keyed by ID and invalidates derived collision/navigation caches; it never deletes catalogue entries. Composite navigation is built from the exact union of active forbidden rectangles, not from a pair-separation shortcut.

    5. How does procedural generation work?¶

    5.1 What does the generation profile contain?¶

    The caller supplies every generation number in ArenaGenerationProfile: the arena fields from section 3, MinimumObjectGap, BoundaryClearance, and a placement class for solids, voids, and hazards. A class has Budget, MinCount, MaxCount, and a canonically ordered weighted pool. Entries have content ID, kind, positive Q16.16 width/height, positive cost/weight, and the kind payload.

    Shared profile validation requires:

    • 0 < MinCount <= MaxCount for each of the three classes;
    • positive costs and weights, a positive MinimumObjectGap, non-negative boundary clearance, and representable fixed operations;
    • the sum of eligible weights to fit positive int32 for IntN.

    The concrete v10 targets are Solid 14..20, Void 6..10, Hazard 8..14: up to 44 gameplay footprints, of which at most 30 affect navigation. MinCount is a density target and telemetry threshold, not an arena-validity condition. A class keeps drawing under section 5.2 until MaxCount, budget/pool exhaustion, or its finite attempt bounds; a shortfall is accepted and reported in generation telemetry. It produces neither a typed runtime error nor a caller retry. CI MUST generate the default profile for the fixed corpus N = 256 seeds 0..255 at one fixed encounter ID and assert zero class shortfall and zero construction errors across the corpus. This is a deterministic content-calibration gate, not an arena-validity rule; the generator already receives and consumes the dedicated encounter-generation stream (server/internal/sim/arena_generate.go:79-87).

    BoundaryClearance remains an art/composition control that keeps generated terrain away from the perimeter silhouette. MinimumObjectGap remains a gameplay/readability control over movement rhythm between disjoint set pieces. Neither is a connectivity proof, and v10 imposes no lower bound tying either one to MaxSupportedBodyRadius or SpawnLatticeStep. The round-4 acyclic-component rule is deleted. Exact placement guards, not gap or cluster shape, own correctness.

    The simulation imposes no 2 m divisibility or minimum footprint size. The current Wang asset publisher imposes those presentation constraints in section 10.

    5.2 What is the RNG and placement order?¶

    Generation uses only RNG system 1. The stream derivation and committed-choice rule are existing contracts (RNG contract). Classes run Solid, then Void, then Hazard.

    Within a class:

    1. Build the eligible, non-exhausted pool in canonical content order from entries affordable by the remaining budget.
    2. Stop if it is empty or MaxCount is reached.
    3. Select one entry with one IntN(sum_weights) draw over cumulative half-open intervals.
    4. Try it at most 64 times; every attempt consumes X then Y before geometry tests.
    5. Draw each candidate minimum uniformly from its inclusive legal raw-coordinate interval. Compute span = hi-lo+1 in int64, require 1 <= span <= 2147483647, then cast to int32. IntN accepts a positive int32 bound (server/internal/rng/rng.go:181-197). Checked addition forms maximum coordinates. There is no rotation.
    6. Accept the first candidate passing sections 5.3 and 5.4, subtract its cost, and increment the count.
    7. After 64 failures, exhaust only that pool entry for the class. Consumed draws remain consumed.
    8. Stop the class under step 2 even when fewer than MinCount placements exist; record the shortfall and accept it.

    There is no random count draw, whole-arena retry, seed mutation, or procedural decoration. A skipped candidate is an ordinary committed RNG outcome: consumed draws remain consumed and generation continues on the one RNG-system-1 stream. The shipped stream contract already makes committed choices consume draws without rewind (RNG contract).

    5.3 Which checks run for each candidate?¶

    Per attempt, perform only checks local to the candidate:

    • checked boundary clearance and positive AABB;
    • duplicate canonical key and kind/payload validity;
    • one scan of existing gameplay footprints for exact AABB gap;
    • strict intersection with any required-clearance circle, and the exact section 7.1 local-site predicate for every provisional generator spawn witness.

    Composite contact/overlap is legal. For two disjoint footprints, exact Euclidean AABB distance must be at least MinimumObjectGap; distance zero is the deliberate composite exception. Use dx = max(0, A.min_x-B.max_x, B.min_x-A.max_x) and analogous dy, and compare uint64(dx)^2+uint64(dy)^2 to the exact uint64(MinimumObjectGap.Raw())^2 under the section 2 span proof. Equality is allowed.

    Hazards stop after these checks because they do not change forbidden free space. A solid or void candidate then runs section 5.4. Do not build the weighted visibility graph or run spawn assignment per candidate.

    5.4 How are connectivity and finalization enforced?¶

    After tentatively adding every solid or void candidate that passes section 5.3, run the exact forbidden-union component algorithm in section 6.1 step 3. Skip the candidate unless that algorithm succeeds; consumed draws remain consumed and the arena is not retried.

    Placement invariant: after every committed solid or void placement, the representable maximum-radius free-centre set is non-empty and has exactly one component. The empty-placement base case is the validated non-empty inset rectangle. The induction step holds because a candidate commits only after the exact post-placement component test establishes the same statement.

    After all three classes, canonicalize once and build the digest-keyed exact union, visibility graph, complete site set, connectors, and spawn reserve metadata for the returned bundle. Debug builds MAY assert the exact-component, static-graph, site-attachment, site-capacity, and synthetic-assignment postconditions, but every release build MUST evaluate them too. Failure returns a typed error and no bundle; it never panics, continues with a partial cache, silently accepts, retries the arena, or mutates the seed. A connector-less site or non-finite required spawn route returns GenerationUnreachableSpawn; other construction inconsistencies return a typed generation-construction error. Structural profile/artifact errors remain ordinary validation errors before generation, and authored presets run the complete shared validation authoritatively because they did not pass through placement guards.

    6. How are reachability and paths computed exactly?¶

    6.1 How are the forbidden union and coordinate nodes built?¶

    Build exactly one derived graph, at MaxSupportedBodyRadius:

    1. Inset Boundary by the radius.
    2. Inflate every active solid AABB by the radius with checked int64 coordinates. Void uses its original AABB because its centre is forbidden.
    3. Compute the exact closed union of all inflated solids and void rectangles. Touching and overlapping composites are one forbidden union. Free-space component analysis is over representable raw centres: vertices are free (int32 raw_x, int32 raw_y) pairs in the inset, and an OPEN edge joins two vertices iff each coordinate differs by at most one raw unit, at least one differs, and their closed segment stays outside the union. Determine its components without enumerating the raw lattice as follows:
    4. Compression. Clip each of the at most R = 30 forbidden rectangles to the inset and ignore an empty clip. For each axis collect the inset minimum and maximum plus each clipped rectangle's min-1, min, max, and max+1, computing the offsets in int64 and clamping them to the inset before narrowing. Sort and deduplicate. Each axis has at most 4R+2 = 122 coordinates.
    5. Cells and structure. For sorted X coordinates, cell column i is the inclusive integer interval [X[i], X[i+1]-1], or [X[last], inset.max_x] for the last column; discard an empty interval. Rows use the identical Y rule. These intervals partition every inset lattice point, and rectangle membership is constant within each Cartesian-product cell because every min and max+1 transition was retained. Scan rectangles in ascending object ID, mark a cell covered when its lower-left lattice point is in the closed union, and create one union-find element for every other cell.
    6. Adjacency and order. Traverse rows by increasing Y index and columns by increasing X index. For each uncovered cell, examine already visited neighbours in fixed West, South-West, South, South-East order and merge only when the two cells contain endpoints of an OPEN edge defined above. Cardinal neighbours test the unit edge at the smallest raw coordinate along their common side; diagonal neighbours test only the corresponding one-raw diagonal segment. Attach the larger root ID to the smaller root ID. Closed cell bounds touching only at a corner never cause a merge. Consequently two free regions meeting only at a covered shared corner remain disconnected, while the free points (101,100) and (100,101) in the one-raw pinch merge through their OPEN diagonal edge.
    7. Result and cost. Scan roots again in the same row-major order, considering only components that contain at least one free lattice point. Require exactly one non-empty root. With C <= 122^2 = 14,884, coordinate work is O(R log R), coverage classification is O(CR), union/find work is O(C alpha(C)), and memory is O(C); equivalently the bounded dominant term is O(R^3).

    For a procedural candidate, skip it unless this result succeeds; for an authored artifact, REJECT on the same failure. In raw coordinates, the four closed rectangles [100,100,101,104], [103,100,104,104], [100,100,104,101], and [100,103,104,104] enclose the free point (102,102). Their rectangle transitions create covered ring cells, so union-find reports the interior root separately from the exterior root. An open corridor one raw unit wide with no legal integer-raw centre between its closed sides does not connect roots. Raw coordinates are signed Q16.16 integers and one metre is exactly 65,536 raw units (server/internal/fixed/fixed.go:1-18,26-34). 4. At every coordinate where union-outline edges meet, classify the four open local quadrants symbolically from the closed rectangle union; do not sample a floating epsilon. Exactly one occupied quadrant is a convex vertex. First test the one-raw outward diagonal in the opposite quadrant. If that diagonal lies inside a different forbidden footprint, also test the two one-raw axis-adjacent alternatives toward that opposite quadrant; retain each alternative that is inside the inset and outside the closed union. This adds (101,100) and (100,101) for inflated A = {x <= 100, y <= 100} and B = {x >= 101, y >= 101}, even though A's diagonal (101,101) lies in B and B's diagonal (100,100) lies in A. Exactly two opposite occupied quadrants are a pinch and test both one-raw diagonals in the empty quadrants. Two adjacent occupied quadrants are flat/collinear; zero, three, or four occupied quadrants are non-convex/interior. Those cases emit nothing. Every candidate offset is retained only if it is inside the inset and outside the closed union. 5. Sort retained offsets by (raw_x, raw_y) and remove duplicates. Each source rectangle corner causes at most three candidate offsets: its outward diagonal and two axis-adjacent fallbacks. With at most R = 30 active navigation footprints, at most 12R = 360 offsets can therefore survive under the conservative charge bound. Exceeding 360 is a construction failure, never truncation or content rejection. Add each inset-boundary corner that is outside the union and every valid required position, sort/deduplicate the complete candidate set by the same key, and assign node IDs in that order. Coordinates alone are node identity; source category, object ID, corner, site index, and required ID live only in separate source-to-node mappings. 6. Add an undirected edge between node pairs whose closed segment stays inside the inset boundary and does not enter or touch the closed forbidden union. Edge weight is exactly floor(sqrt(uint64(dx)^2+uint64(dy)^2)), narrowed with fixed.FromRaw64Checked. The section 2 diagonal bound gives |dx|,|dy| <= 2^31-1, keeps the squared sum below 2^63, and guarantees the resulting weight is at most 2^31-1. Maximum-radius path distance is the sum of these integer hop weights in int64; it is not an approximation contract to be replaced by another length rule. 7. Run a component check over all static nodes in every build. A procedural failure returns a typed generation-construction error and no bundle; an authored artifact REJECTS. A debug build MAY additionally assert after the checked path. Section 7.1 applies the same release-safe rule after adding site attachments. This is independent of required-clearance count and therefore also runs when there are zero required positions. The shipped v9 validator likewise rejects when any navigation node is unreachable from its first node (server/internal/sim/arena_layout.go:270-286).

    The conservative 360-offset bound, at most four boundary corners, and at most four required positions give static V <= 368; final coordinate deduplication can only lower it. A woven union can create quadratically many outline intersections and holes, but those intersections are flat/concave rather than new exposed input corners, and step 3 skips the procedural placement or rejects the authored artifact that would leave an extra representable component. Future mutable geometry rebuilds and revalidates the one maximum-radius union and graph and MUST still respect R <= 30.

    For a dynamic point, reuse an equal coordinate or add one temporary node and connect it to the same maximum-radius graph by the same predicate. Dijkstra accumulates in int64. Equal tentative distances settle lower node ID first; equal-distance predecessor choice uses the lexicographically smaller complete node-ID path. No query consumes RNG.

    6.2 How is graph work bounded?¶

    Validation builds and caches only the maximum-radius graph. Every initial participant uses it; a smaller radius enlarges free space and can merge components but cannot split the single component already proved at the maximum radius. No exact-radius graph is built. Spawn lattice points never become permanent static nodes; section 7.1 streams them once through maximum-radius temporary-node connector tests and retains their connector lists in the digest-keyed cache.

    Build one deterministic interval index over forbidden rectangles, with raw interval endpoints and object ID as the stable tie-break. Before any static-edge or site-connector segment/rectangle predicate, shortlist only rectangles whose closed X interval and closed Y interval both overlap the segment's closed AABB, then run the exact predicate on that shortlist in ascending object ID. A rectangle outside that AABB cannot meet the segment, so this broad phase has no false negatives and cannot change nodes, edges, connectors, weights, or ties.

    The implementation and ArenaLab MUST report, without turning telemetry into acceptance rules: candidate counts by class and outcome; MinCount shortfall; compressed coordinate/cell/root counts for every component test; interval-shortlist sizes; exact segment/rectangle predicate counts split among static edges, site connectors, and dynamic attachments; graph nodes/edges; connector-less sites; Dijkstra runs, settled nodes, and relaxations; and cache builds versus hits.

    A cache-hit Run performs no graph or site rebuild; preset load and restore each rebuild once. This replaces the shipped flow that resolves during Run construction (server/internal/sim/run.go:36-55; server/internal/sim/state.go:40-63). Per tick, cached graph construction and lattice streaming cost zero. Site connector lists and multi-source distance fields are derived once for the maximum radius; no all-pairs site graph is built. A route can detour arbitrarily around a void chasm relative to the direct distance; v10 deliberately sets no route-length content cap. That is accepted for the default 60 m × 40 m arena under the engine's absolute stop at tick 18,000 (server/internal/sim/tick.go:259-270); distances still accumulate in int64 and every fixed narrowing remains checked.

    7. How are spawn sites derived and assigned?¶

    7.1 How are lattice sites derived?¶

    Enumerate the lattice from (Boundary.min_x, Boundary.min_y) with positive SpawnLatticeStep, X then Y using checked int64. Canonical site order is (raw_x, raw_y).

    Before consuming generation RNG, profile validation enumerates that lattice in the empty boundary and deterministically finds the lexicographically smallest ordered tuple of HeroSpawnCapacity + EnemySpawnCapacity points that each satisfy the boundary part of the local-site predicate below and whose maximum-radius body circles are pairwise non-overlapping. The search visits candidate indices in ascending order and is bounded by the at-most-six capacity in section 3.2; no such tuple is an invalid generation profile, not a failed arena attempt. The tuple is the generator's provisional witness reserve. Every object candidate, including a hazard, is skipped if it would make a provisional witness fail the complete local-site test below. Under the default profile, all six provisional witnesses consequently occupy the lexicographically earliest feasible min-X corner column. This harmless bias affects only the hidden existence reserve; final assignment still uses the quality order in section 7.2.

    A locally valid point must let a circle of MaxSupportedBodyRadius + SpawnClearance fit inside the boundary without strict overlap with an active solid, and its centre must be outside active hazard and void AABBs. Derived clearance is the minimum raw distance to the boundary and active solid/void AABBs, using the section 2 uint64 square bound and the existing integer square root.

    Connect each locally valid point as a temporary attachment node to every visible static node of the maximum-radius graph. The axis-adjacent fallback in section 6.1 closes the demonstrated one-raw pinch, but v10 does not claim a proof that these visibility nodes are complete for every overlapping/touching rectangle union and every lattice attachment. Therefore a connector-less procedural site or non-finite procedural spawn route returns typed GenerationUnreachableSpawn in debug and release builds, with no arena retry; authored artifacts reject when there is no locally valid site, a site has no connector, or the combined graph is disconnected. There is no component selection, pocket acceptance, or component tie-break.

    The complete resulting list is a derived view. Authored presets do not supply or byte-compare it.

    After deriving the final complete site list, select the cache's spawn-witness reserve as the lexicographically smallest ordered tuple of the stored total capacity whose maximum-radius body circles are pairwise non-overlapping. A procedural artifact always has at least one such tuple because its provisional witnesses survived every placement. An authored artifact rejects if no tuple exists. This final reserve, rather than the provisional generator tuple, is rebuilt from artifact fields and is not stored in canonical bytes.

    7.2 How are participants assigned?¶

    Participants arrive sorted hero first, then entity ID. Reject non-positive radius, radius above MaxSupportedBodyRadius, or side counts inconsistent with stored capacities. For valid participant input, the final spawn-witness reserve guarantees that body overlap cannot eliminate every candidate.

    1. First hero: among candidates passing the reserve-completability filter in step 5, greatest derived clearance, then lowest site index.
    2. Additional heroes do not exist in v10 initial encounters.
    3. Every maximum-radius path distance used by assignment must be finite. A non-finite distance returns typed GenerationUnreachableSpawn and no partial assignment.
    4. For every enemy, among candidates passing step 5, maximize the minimum maximum-radius path distance to the hero and to every already assigned enemy, then maximize maximum-radius path distance to the hero, then clearance, then lowest site index. With no enemy assigned yet that minimum is the hero distance alone, so the first enemy still takes the hero-farthest site. That leading minimum is the normative minimum-separation criterion between enemies: ranking by the hero distance first and letting enemy separation act only as a tie-break collapses the whole pack onto the single hero-farthest cluster, one lattice step apart, which is not an acceptable initial encounter. The criterion is a maximin over the already placed participants, so it needs no separation constant, stays integer, and consumes no RNG.
    5. A site is admissible only when its body circle does not overlap an assigned body; equality at (r1+r2)² is legal. It is rankable only if, after tentatively choosing it, enough unused spawn-witness sites remain non-overlapping with every chosen body to fill all remaining roster slots. Because the witnesses are mutually non-overlapping and remain locally valid, this deterministic reserve-completability filter guarantees that at least one rankable choice exists at every step while retaining the stated quality ordering among safe choices.
    6. Failure of the reserve-completability existence guarantee returns a typed generation-construction error in every build. Fresh input still rejects invalid participant radii/counts or a participant roster inconsistent with stored capacities. GenerationUnreachableSpawn remains reserved for missing connectors or non-finite routes.

    For one assignment step, use the cached maximum-radius site connectors and one hero-source and one assigned-enemy multi-source distance field. Do not construct a participant-radius graph or run a separate Dijkstra for each candidate. Assignment consumes no RNG.

    8. How do void and falling work?¶

    8.1 How does void membership treat dead entities?¶

    Void uses inclusive centre membership, not body overlap. Lowest object ID wins simultaneous membership. Initial/restored state rejects an Alive == true entity centred in void.

    Alive, not Health, controls falling. An Alive == false corpse is inert, is not swept or tested for a new fall, may restore in void, and emits no second death. An entity reduced to zero health in stage 5 remains alive through stages 6–8 and can fall; void then takes cause precedence in stage 9. Existing movement skips dead entities and death is deferred (server/internal/sim/tick.go:236-256,288-297).

    8.2 Which trajectory is swept?¶

    For each living entity, record exactly one possible directed segment: the position immediately before stage 6 to the position committed by stage-6 movement. Stage-7 participant depenetration and every stage-8 obstacle correction, boundary clamp, closing sweep, or fallback are geometric projections, not physical trajectories (server/internal/sim/collision.go:46-85; server/internal/sim/bounds.go:73-107). They must never be swept.

    After stage 7 commits, test its final centre by point membership. After stage 8 commits, test its final centre again. A boundary clamp that lands inside void falls by membership, but the clamp vector does not cross anything. A stage-8 fallback to the tick-entry origin cannot create a false crossing; the current fallback really does restore that origin (server/internal/sim/tick.go:60-64,83; server/internal/sim/bounds.go:94-106). The first stage-6 sweep hit takes precedence, then the stage-7 landing, then the stage-8 landing; within a check, lower void object ID wins.

    The stage-6 segment uses exact closed Liang-Barsky clipping. Raw coordinates are int32 (server/internal/fixed/fixed.go:70-77), so every endpoint/boundary difference has magnitude at most 2^32-1. Normalize signs into uint64 numerator/positive-denominator pairs; comparing a/b and c/d uses a*d versus c*b, each below 2^64. The tick path allocates no big.Int. math/big.Int remains permitted only in off-tick generator predicates, as the current exact generator does (server/internal/sim/arena_generate.go:325-385).

    8.3 How is a pending fall resolved?¶

    The first hit creates a tick-local pending fall that later correction cannot cancel. In stage 9, entities are processed by ascending ID. Pending fall precedes health depletion and:

    • sets health to zero and Alive = false, clears action, and zeroes velocity;
    • emits one ordinary death event with Cause = VoidFall and the void object ID;
    • uses SourceEntityID = 0, including knockback-caused movement;
    • participates in the same side-wipe verdict.

    The death payload becomes (EntityID uint64, Cause uint8, CauseObjectID uint64, SourceEntityID uint64), with causes HealthDepleted=1, VoidFall=2. Non-death canonical events write zeroes in the added fields. The current stage batches deaths in entity order and retains statuses (server/internal/sim/tick.go:272-313).

    8.4 Which void facts can AI observe?¶

    Solid, hazard, and void footprints are public to both sides. The route service treats void as forbidden. NearestVoid(point) returns presence, lowest-ID nearest void, and floor Euclidean point-to-AABB distance. NominalPushEntersVoid(target, delta) runs the same stage-6 segment predicate on the nominal checked displacement. These facts expose no future RNG, Brain choice, hit result, or collision projection.

    9. How does quicksand dwell affect status lifecycle?¶

    9.1 Which IDs, state, and tempo floor are mandatory?¶

    Terrain statuses need no source/tag byte. The ID itself reserves the namespace:

    0x00000000                  invalid
0x00000001..0x7fffffff      ordinary status IDs
0x80000000                  reserved, invalid terrain sentinel
0x80000001..0xffffffff      terrain status IDs

    For object ID 1..0x7fffffff, a hazard's status ID is 0x80000000 | uint32(object_id). It is unique and derived, so StatusID is not stored in the object. The shared fresh-input and restore validator MUST reject ID zero; MUST classify only 1..0x7fffffff as ordinary; and MUST reject any high-bit status unless it satisfies every terrain invariant and maps to the active hazard encoded by its low 31 bits. Ordinary-status creation paths MUST reject the high bit before insertion. This is new validation: the shipped validator checks ordering and expiry but accepts arbitrary canonical uint32 IDs (server/internal/sim/state.go:223-236,263-291; server/internal/sim/canonical.go:74-78,294-299).

    type Status struct {
    ID             uint32
    ExpiresAt      uint32
    DwellHalfTicks uint32
}

    Ordinary statuses require DwellHalfTicks == 0. Terrain statuses require DwellHalfTicks >= 1, map back to an active hazard object, and between ticks have ExpiresAt == Tick + 1.

    The mandatory tempo floor is TerrainTempoFloorRaw = fixed.ONE / 4 = 16384. For a hazard with ramp = RampLossPerTick.Raw():

    ticks_to_floor = ceil((65536 - 16384) / ramp)
half_cap       = 2 * ticks_to_floor
dwell_half     = min(previous_dwell_half + 2, half_cap)
dwell          = dwell_half / 2
loss           = min(uint64(dwell) * uint64(ramp), 49152)
tempo_raw      = 65536 - loss

    All values are integer; division truncates and the bounded product fits uint64. A new membership starts at DwellHalfTicks = 2. With no retained terrain status, effective tempo is exactly fixed.ONE == 65536; otherwise it is the minimum tempo of all retained terrain statuses, including a status currently decaying outside its patch. The constant is defined at server/internal/fixed/fixed.go:26-34.

    The floor guarantees windup advances by at least 16384 raw per affected tick, so one nominal windup tick completes within four slow ticks instead of stalling until absoluteStopTick == 18000 (server/internal/sim/tick.go:259-270). Because MulChecked truncates each component toward zero (server/internal/fixed/fixed.go:144-154), raw component magnitude 4 is the minimum that remains non-zero at the floor. V10 explicitly accepts that components with magnitude 1..3 become zero and an otherwise living entity may remain immobile until the absolute stop; there is no minimum-speed content rejection.

    9.2 How does the stage-1 reconciliation pass work?¶

    At stage 1, process every entity by ascending ID. For a living entity only, process hazards by object ID, sample inclusive tick-entry centre membership, and build encountered terrain IDs. A dead entity has an empty encountered set but still runs the same ascending-status-ID merge pass:

    1. encountered existing terrain status: add 2 to DwellHalfTicks, cap at half_cap, set ExpiresAt = Tick + 1, and keep it;
    2. non-encountered existing terrain status: decrement DwellHalfTicks by 1. If it becomes zero, remove it and emit exactly one expiry event; otherwise set ExpiresAt = Tick + 1 and keep it;
    3. ordinary status with ExpiresAt <= Tick: remove it and emit exactly one expiry event;
    4. otherwise keep the ordinary status;
    5. insert newly encountered terrain IDs in ascending order with DwellHalfTicks = 2 and ExpiresAt = Tick + 1.

    Do not call a second generic expiry pass. The shipped expireStatuses visits all entities, uses ExpiresAt <= Tick, and emits during removal (server/internal/sim/tick.go:98-111); v10 replaces it with this single all-entity reconciliation. Death deliberately retains statuses (server/internal/sim/tick.go:282-296), so a corpse's ordinary statuses still expire and its terrain statuses decay to removal here.

    Ramp and decay are deliberately asymmetric integer rates: membership adds two half-ticks per inside sample, while absence removes one half-tick per outside sample. Tempo uses DwellHalfTicks / 2 with truncation, and removal occurs only at zero. A retained one-half-tick status therefore applies zero loss for its final retained tick. Crossing a patch entirely between samples still creates no status. Dead entities are never refreshed and therefore decay as continuously absent.

    Overlapping patches keep independent dwell because status ID is per object. Effective tempo is the minimum current or decaying patch rate; rates never multiply. Thus the strongest retained slow wins deterministically.

    9.3 How are movement and windup scaled?¶

    Stage 6 computes the ordinary-plus-forced displacement, then scales X and Y once by effective tempo through fixed.MulChecked. Any saturation aborts the run. Stored velocity/knockback are not overwritten, and stage-7/8 projections are not scaled.

    Authored Windup remains integer ticks. Running WindupRemaining is Q16.16, initialized as checked Windup * fixed.ONE. Each later stage 2 subtracts effective tempo, clamps at zero, and reaches impact on the tick it becomes zero. For zero windup, stage 4 MUST set PhaseImpact directly rather than waiting for stage 2, so stage 5 resolves the impact in the start tick; this is the shipped stage ordering and instant-action transition (server/internal/sim/tick.go:33-45,135-160,173-187).

    10. How is the presentation grid published?¶

    The current presentation publisher uses 2 m × 2 m cells (arena asset contract; codedungeon/assets/arena/arena_asset_contract_v1.json:18-22). Publication—not simulation artifact validation—therefore requires boundary spans divisible by 2 * fixed.ONE and hazard/void footprints at least 2 * fixed.ONE on both axes. Changing wang_cell_metres changes publication acceptance only; it does not change simulation version or which artifacts the simulator can validate.

    Published cells are row-major from minimum Y, with half-open interior ownership and inclusive outer maximum edges. Sample N/E/S/W edge midpoints. Independently derive Hazard, Void, and Solid bits; emit the existing fill/transition signatures and composite in that order, so visible priority is Solid over Void over Hazard over walkable. The asset contract defines the roles and 46 signatures (codedungeon/assets/arena/arena_asset_contract_v1.json:122-184).

    The grid is never read by collision, void, hazard membership, navigation, spawn derivation, AI, canonical state, hash, or RNG. Unaddressed decoration is layered entirely by the client.

    11. How are presets encoded and restored?¶

    An authored preset supplies the same ArenaDefinition; it does not supply spawn sites, zones, portals, provenance, or decoration. Q16.16 fields are signed raw int32 decimals. Unknown fields, duplicate keys, duplicate object canonical keys, and invalid UTF-8 reject.

    Canonical artifact bytes are little-endian and count-prefixed:

    1. uint32 canonical_version = 10;
    2. four boundary raw int32 values;
    3. raw maximum radius, spawn step, spawn clearance, uint32 hero capacity, uint32 enemy capacity;
    4. object count, then each canonical object: four AABB raw values, namespace length/bytes, content value, kind (Solid=1, Hazard=2, Void=3), initial activity byte, raw ramp loss.

    That is the whole encoding, and it is exactly the stored list of section 3.4. There is no spawn-site section, no required-clearance section, no decoration kind, and no merged collision view: the contacts are derived (section 3.4) and are a pure function of the boundary and the catalogue above, so hashing them would commit a view that adds no identity while making any later refinement of the merge rule look like a different arena. Decoding therefore re-resolves through the single producer path, which reassigns the object IDs, rebuilds the collision view, and validates the artifact. Publication requires decode -> validate -> encode byte equality and a committed SHA-256. Two producers resolving the same definition produce identical bytes.

    Canonical entity status bytes append DwellHalfTicks uint32 after the existing ID and ExpiresAt; ordinary statuses write zero. Action.WindupRemaining is encoded and decoded as raw Q16.16 int32.

    The v10 digest wins over the v9 stage-8 section: per-tick canonical state stores the cached 32-byte artifact digest immediately after encounter_id, replacing rather than accompanying the inline boundary-plus-contacts bytes. The old section currently occupies exactly that position (server/internal/sim/canonical.go:50-57,110-126; combat engine). A recovery/replay capsule carries immutable artifact bytes once alongside snapshots. Restore decodes and validates the artifact, verifies its SHA-256 against the state digest, then rebuilds boundary, contacts, graph, sites, connectors, indexes, and all other derived views into a cache keyed by that digest. A digest mismatch rejects atomically. When destruction ships, canonical state adds the real mutable activity/durability vector; it still does not repeat immutable catalogue bytes every tick.

    The current server/internal/sim/arena_layout.go:390-497 is the complete artifact encoder and decoder, not a deletable zone-only range: framing and object encoding are 390-403, layout encoding is 405-431, and decoding is 438-497. V10 retains/refactors the whole codec and replaces only v9 layout fields.
