    Как локальное состояние сохраняется и восстанавливается?¶

    Эта глава задаёт единственный локальный контур долговечного состояния: владение SQLite, границы repository, атомарную запись, проверку загрузки, backup и миграции профиля, персонажей, Мозгов и незавершённого забега.

    Реализует: принадлежность персонажей и Мозгов профилю, совместимость ревизий Мозга, checkpoint незавершённого забега, постоянное развитие после попытки.

    Где находится источник истины?¶

    Локальный Go-процесс единолично владеет рабочей SQLite-базой и открывает её до запуска игровых application services. Godot никогда не открывает файл базы, не выполняет SQL и не хранит snapshot, пригодный для восстановления игровой истины. Клиент отправляет намерения и после commit получает новую серверную проекцию; закрытие окна, смена сцены или локальный cache не меняют сохранённое состояние.

    SQLite работает в WAL mode. Адаптер включает foreign keys, допускает одного writer, держит изменяющие транзакции короткими, использует подготовленные batch statements для групповых записей и выполняет checkpoints так, чтобы WAL не рос без контроля. База, открытый WAL и SHM образуют одну работающую единицу: копировать только основной файл во время работы процесса запрещено.

    В SQLite входят профиль и все принадлежащие ему игровые агрегаты. Профиль связывает общий сундук, постоянные ресурсы и открытия, доступную Память, библиотеку Мозгов и несколько персонажей; персонаж связывает собственное развитие, билды, экипировку, назначенную ревизию Мозга и активную попытку. Граница принадлежности следует игровым главам выше: persistence сохраняет её, но не определяет заново.

    Активная попытка хранится как состояние, которое передаёт оркестратор забега. Persistence не конструирует карту, encounter inputs, награду или checkpoint и не меняет их смысл при загрузке. Детализация SQLite-записи checkpoint следует записи реестра о checkpoint узла; до её закрытия адаптер хранит только целый версионированный объект владельца домена и не вводит собственные поля.

    Immutable content packages и файлы replay не являются строками локального save. Их форматы и совместимость принадлежат соответственно пакетам контента и replay; база хранит только необходимые ссылки на закреплённые версии и hashes. Пользовательские настройки Godot принадлежат архитектуре клиента, а не gameplay-базе.

    Как домен обращается к хранилищу?¶

    Игровые пакеты зависят от малых repository-портов, а не от SQLite driver, SQL-запросов или структуры таблиц. ProfileRepository обслуживает профиль и состав его персонажей, repository Мозгов — библиотеку и неизменяемые ревизии, порты build/progression/run — свои агрегаты, а Store из пакета itemstore — экземпляры предметов, расположение и идемпотентные операции. SQLite adapter реализует эти порты и общий transaction boundary; тестовые адаптеры в памяти исполняют тот же contract suite, но не заменяют локальную production-базу.

    Каждый порт принимает context.Context, идентичность владельца, ожидаемую revision там, где агрегат изменяем, и уже проверенный доменный объект. Чтение возвращает целую копию агрегата либо различимый исход «не найдено»; изменение возвращает зафиксированную revision и результат команды. Version conflict, невалидные данные, занятость writer и ошибка storage различаются машинно, чтобы application layer мог повторить только безопасный отказ и не выдавал внутреннюю ошибку за игровое ограничение.

    Repository не вычисляет стоимость крафта, вместимость сетки, допустимость билда, награду, переход карты или корректность графа Мозга. Эти проверки выполняют владельцы домена до начала записи и повторяют над данными, прочитанными внутри транзакции, если результат зависит от revision. Persistence проверяет собственные ограничения schema, ссылочную целостность и optimistic concurrency, а затем фиксирует переданный change set целиком.

    Успешный application event или новая клиентская проекция становятся видимы только после commit. Ошибка до commit не публикует событие, не увеличивает revision и не оставляет idempotency record успешной операции. Повтор команды с тем же ключом возвращает сохранённый outcome без второго расхода или награды; использование того же ключа для иного намерения отклоняется.

    Где проходит граница транзакции?¶

    Транзакция охватывает весь инвариант одной команды, даже если он пересекает несколько repository. Крафт одновременно расходует ресурсы и записывает предмет, salvage одновременно удаляет предмет и начисляет материал, применение результата узла вместе меняет попытку, переносимое состояние героя, добычу, прогрессию и отметку идемпотентности. Назначение Мозга записывает ссылку только на уже существующую проверенную ревизию; создание ревизии и её включение в библиотеку не допускает ссылки на отсутствующего родителя.

    Запись использует одну writer transaction и стабильный порядок захвата изменяемых records. Каждый update изменяемого агрегата сравнивает ожидаемую revision; несовпадение отменяет всю команду. Частичный commit между repository, компенсационная «обратная» команда после неудачи и изменение одной таблицы в обход transaction coordinator запрещены.

    Перед записью adapter получает полностью подготовленный candidate state. Он не сериализует весь профиль одним непрозрачным JSON-документом: идентичность, принадлежность, revision и связи остаются доступными ограничениям и запросам SQLite, а редко читаемая структурированная часть может лежать в компактном payload с собственной codec version. Для ItemInstance payload начинается с версии codec, целые без знака кодируются unsigned varint, знаковые rolls — zig-zag, а естественные boolean-состояния разделяют поле flags; ручная межполевая упаковка по битам не вводится.

    Что проверяется при загрузке?¶

    Загрузка сначала читает данные во временное состояние, затем последовательно проверяет database schema, версии payload, обязательные значения и типы, диапазоны, известность enum и стабильных ID, уникальность, ссылки, конечность чисел, ограничения размеров и глубины и межполевые инварианты. После storage-проверок каждый объект проходит валидатор своего доменного владельца: предмет — registry текущего закреплённого контента, Мозг — авторитетный validator, build и checkpoint — соответствующие порты систем забега. Только полностью проверенный набор заменяет живое состояние процесса.

    Неизвестная будущая версия, отсутствующая content reference, повреждённый payload, нарушение foreign key или ошибка любого доменного валидатора проваливает загрузку целиком. Adapter не отбрасывает отдельное поле, не подставляет default, не выбирает похожий ID и не начинает новый забег вместо повреждённого. Исходные данные сохраняются для диагностики, а ответ указывает область, объект и машинно-различимую причину без вывода содержимого Мозга или всей базы в лог.

    Мозг не служит необязательным дополнением к профилю. Если библиотека, назначение или одна достижимая ревизия не проходит загрузку либо миграцию, профиль не открывается частично. Локальный незавершённый draft Godot также не подменяет сохранённую ревизию: persistence принимает только объект, проверенный runtime Мозга.

    Как создаётся backup и проходит восстановление?¶

    Перед заменой текущего валидированного состояния адаптер сохраняет как минимум один предыдущий валидированный state. Источником backup может быть только состояние, которое уже успешно загрузилось и прошло полную storage- и domain-валидацию; неудачная запись, повреждённый импорт или проваленное восстановление в ротацию не попадает. Конкретное число дополнительных копий не является частью контракта.

    Порядок изменяющей операции фиксирован: проверить candidate state, сохранить предыдущий валидированный state как backup, открыть одну транзакцию, записать все изменения, проверить ссылки и инварианты и только затем выполнить commit. Сбой на любом шаге оставляет прежнее валидное состояние либо полностью новое. Backup должен быть согласованным SQLite snapshot; копия открытого основного файла без связанного WAL таким snapshot не считается.

    При невалидной загрузке игра не продолжает работу на частично восстановленных данных. Пользователь получает диагностику и может явно выбрать восстановление из самого свежего backup, который сам проходит полную проверку, либо создать новый профиль. Ни восстановление, ни создание профиля не запускаются автоматически; невалидная рабочая база остаётся доступна для диагностики и не перезаписывается результатом проваленной попытки.

    Как меняются schema и payload?¶

    Версия database schema, версии payload и доменные версии развиваются независимо. SQL migration меняет таблицы и индексы, codec migration меняет представление payload, а доменная миграция преобразует смысл объекта только через функцию владельца. ContentVersion, версия словаря тегов, vocabulary_version Мозга и replay compatibility не заменяются одним общим номером save.

    Embedded versioned SQL migrations являются единственным источником database schema. Adapter не создаёт недостающие таблицы или колонки побочными запросами и не выводит schema из Go structs при запуске; любое изменение сначала появляется следующим явным migration step и получает fixture старой базы. DDL не копируется в доменные главы.

    При запуске Go-процесс определяет версию базы до выдачи readiness. Известная старая версия проходит явную упорядоченную цепочку миграций внутри транзакции после создания backup; после каждого доменного шага объект снова валидируется. Неизвестная будущая версия, отсутствующий шаг или невалидный результат останавливает запуск gameplay services, откатывает транзакцию и сохраняет исходную базу и backup.

    Миграция Мозга никогда не переписывает существующую ревизию. Runtime создаёт новую проверенную ревизию и сохраняет исходную вместе с родительской связью и каноническим hash; repository только фиксирует переданный объект и его связь. Миграция предмета использует SchemaVersion и Migrate из предметного контракта, не переназначает content ID и не исправляет отсутствующую definition эвристикой.

    После миграции выполняются integrity check, полная загрузка во временное состояние и сравнение обязательных инвариантов. Лишь затем новая schema становится рабочей. Тест migration обязан начинаться с поддерживаемой старой fixture, пройти перезапуск и доказать равенство канонического доменного состояния, а fixture с неизвестной версией обязана завершаться контролируемым отказом без изменения файла.

    • Владелец: Go/симуляция, этап S5 по плану производства. Godot/клиент на S3 работает с fixtures, а на S9 показывает результаты загрузки и восстановления через application contract, не обращаясь к SQLite.
    • Артефакты: repository-порты профиля, персонажа, библиотеки ревизий Мозга, build/progression и активной попытки рядом с их доменными пакетами; пакет itemstore с Store и общим contract suite; пакет itempersist с directional mapping; один Go SQLite adapter с embedded versioned migrations, transaction coordinator, integrity validation, backup/recovery и restart fixtures; временные SQLite-базы для positive, corruption, rollback и migration tests.
    • Готово, когда: база открывается в WAL mode только Go-процессом и до readiness проходит migration, integrity check и полную загрузку; profile с несколькими персонажами и библиотекой Мозгов переживает save–restart–load без изменения канонического состояния; активная попытка открывается на том же checkpoint с теми же закреплёнными входами; item, build, progression и run проверяются отдельными тестами; stale revision, повтор idempotency key и injected failure не дают второй награды, расхода или частичной записи; невалидный объект и неизвестная версия отклоняют весь профиль; backup создаётся только из валидного state и восстанавливается только после полной проверки; миграция Мозга сохраняет исходную ревизию; один contract suite проходит для тестового адаптера в памяти и SQLite adapter; go test ./... -race из корня Go module и критерии S5 проходят.
    • Не трогать: gameplay-смысл профиля и постоянной прогрессии принадлежит game design; граф, hash, validator и миграция словаря Мозга — brain-runtime.md; item definitions, inventory rules и craft change set — items-and-crafting.md; карта, checkpoint object и применение наград — run-systems.md; replay container и retention — replay.md; content ID, schemas и package lifecycle — content-packages.md; protobuf, opcode и wire evolution — contracts-and-data-flow.md; сцены, локализованная диагностика и пользовательский flow восстановления — client-architecture.md и главам screens/.
