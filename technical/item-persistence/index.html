    Хранение предметов¶

    Решение¶

    Определения предметов — база, metadata аффиксов, локализация, диапазоны и теги — являются неизменяемым контентом, адресуемым стабильными uint32 ID. Экземпляр предмета хранит только идентичность, владельца и расположение, версию, стак, компактные изменяемые значения, RNG seed и пары ID/значение выпавших аффиксов. Строки и данные определений не повторяются в каждом выпавшем предмете.

    server/internal/itemstore — граница адаптера. Игровые правила зависят от Store, а не от драйвера базы данных. Memory служит исполняемой спецификацией и тестовым backend, но не production-базой MMO.

    Контракты неизменяемых определений и чистых операций крафта описаны в документе о контенте предметов и движке крафта. Игровой дизайн принадлежит документу о предметах и крафте.

    Топология базы данных¶

    • Solo/local/offline: решено — SQLite в WAL mode, владелец базы — локальный Go-процесс, Godot её никогда не открывает. Доступ идёт только через repository-порты, поэтому онлайновое хранилище позднее заменяет адаптер, а не правила. Следует использовать одну writer transaction, подготовленные batch statements и периодические checkpoints. Драйвер SQLite выбирается только при реализации адаптера: не следует заранее добавлять CGO или крупную зависимость.
    • Авторитетные co-op/PvP: предпочтительная модель — PostgreSQL-compatible SQL. Она предоставляет row locking, транзакционный крафт и передачи, зрелые replication, backup и operational tooling. Партиционирование по account/owner вводится только после подтверждающих измерений. SQLite нельзя использовать как базу на общем сетевом диске.
    • Redis: допустим позднее для краткоживущих caches и locks, но никогда не является источником истины для предметов во владении игроков.

    Строка базы данных хранит доступные для запросов колонки владельца, расположения и версии, а также компактный версионированный payload для менее часто запрашиваемого состояния экземпляра. Весь предмет нельзя помещать в JSON. Колонки grid_x/grid_y обязательны: рюкзак является сеткой, предметы занимают в ней разное число ячеек, а стаки ресурсов тоже лежат в ячейках сетки и несут stack_count, ограниченный максимальным размером стака своей валюты.

    CREATE TABLE item_instance (
  item_id BIGINT PRIMARY KEY,
  definition_id INTEGER NOT NULL,
  owner_kind SMALLINT NOT NULL,
  owner_id BIGINT NOT NULL,
  location_kind SMALLINT NOT NULL,
  container_id INTEGER NOT NULL DEFAULT 0,
  grid_x SMALLINT NOT NULL DEFAULT 0,
  grid_y SMALLINT NOT NULL DEFAULT 0,
  slot SMALLINT NOT NULL DEFAULT 0,
  stack_count INTEGER NOT NULL CHECK (stack_count > 0),
  version BIGINT NOT NULL,
  payload BYTEA NOT NULL
);
CREATE INDEX item_owner_location
  ON item_instance(owner_kind, owner_id, location_kind, container_id, item_id);
CREATE TABLE item_operation (
  owner_id BIGINT NOT NULL,
  operation_id UUID NOT NULL,
  result BYTEA,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY(owner_id, operation_id)
);

    SQLite использует эквивалентные колонки INTEGER и BLOB. Ключи item_operation делают повторные сетевые запросы идемпотентными; production-адаптеры обязаны хранить или архивировать их как минимум в течение максимального окна повторов.

    Атомарные операции¶

    Передача, экипировка, salvage и craft выполняются внутри Store.Transact. Чтение и запись используют version как optimistic concurrency token. Передача меняет владельца и расположение в одной транзакции. Крафт расходует материалы и изменяет или создаёт результат в той же транзакции, поэтому отключение не может дублировать предметы. Разделение и слияние стака также выполняется одной транзакцией: проверить совпадение definition и stackable state, уменьшить или удалить источник, затем увеличить или создать назначение.

    In-memory реализация сериализует транзакции ради корректности. SQL-адаптер должен использовать SELECT ... FOR UPDATE в стабильном порядке item ID для предотвращения deadlock и UPDATE ... WHERE item_id=? AND version=? для обнаружения устаревших клиентов.

    Будущий Online-рынок — application service над этой границей, а не второй источник истины предметов. Он владеет состоянием лота и выбором покупателя; itemstore владеет идентичностью и владельцем предмета, wallet — доступными и зарезервированными средствами. Settlement должен атомарно и идемпотентно проверить лот и ревизию предмета, передать владение предметом и платёж, закрыть лот, применить блокировку повторного выставления и освободить проигравшие резервы. Catalog projections обновляются транзакционным или outbox-событием с допустимой задержкой, но каждое намерение покупки повторно проверяется по авторитетному состоянию, чтобы устаревшая projection не могла продать предмет дважды. Жизненный цикл лота определяет опубликованный GDD.

    Доверие к локальным данным и валидация загрузки¶

    Решено. Offline-сохранения и контент не защищаются: игрок может править их свободно. Online-персонажи и рынок — отдельный мир с серверной истиной и без импорта из offline.

    Валидация загрузки при этом обязательна всегда:

    • схема и версия, обязательные поля, типы, диапазоны;
    • существование enum и ID, уникальность, ссылки;
    • лимиты размеров массивов и map, конечность числовых значений, лимиты рекурсии и размера;
    • межполевые инварианты.

    Порядок: разобрать во временное состояние, полностью провалидировать и только затем зафиксировать. Частичная мутация живого состояния запрещена. Неизвестные будущие версии отклоняются; известные старые версии мигрируются транзакционно с сохранением backup. Отказ происходит закрыто и с понятной диагностикой: локальная редактируемость никогда не оправдывает падения, зависания или молчаливого «починить само».

    Поведение при невалидном сохранении¶

    Решено. Сохранение, не прошедшее валидацию, не загружается. Игра не чинит, не подрезает и не переосмысливает его молча: это прямое продолжение правила «никакого молчаливого fallback» выше.

    Карантин полей запрещён. Загрузка сохранения с выброшенными или заменёнными на умолчания отдельными полями даёт состояние, которого игрок никогда не создавал. Частично починенное сохранение — это молчаливая подстановка: со стороны игрока оно неотличимо от его собственного прогресса, и обнаружится потеря только тогда, когда её уже не с чем сверить.

    Вместо починки игроку предлагается ровно три исхода, в этом порядке:

    • честная диагностика: что именно не прошло проверку и в какой части сохранения это лежит;
    • восстановление из самого свежего backup, который сам проходит полную валидацию — целостность, ссылки и доменные инварианты, а не «файл открывается»;
    • явный осознанный выбор начать новый профиль.

    Ничего из этого не происходит само: каждый исход выбирает игрок.

    Мозг неприкосновенен. Мозг никогда не выбрасывается, не сбрасывается, не подменяется и не восстанавливается частично ради того, чтобы загрузилось остальное сохранение. Если мозг не удаётся загрузить валидно, загрузка проваливается целиком — остаток сохранения не спасается за счёт мозга. Это следует из опоры проекта: мозг — единый накапливаемый артефакт на всю игру (мозг как накапливаемый артефакт), и частично восстановленный мозг разрушает именно то, что накапливалось. Версии мозга подчиняются версионированию словаря: неизвестная будущая vocabulary_version отклоняется, известная старая мигрируется транзакционно, любой отказ роняет гейт миграции — эвристической догадки о смысле узла не существует.

    Порядок записи, делающий частичную запись невозможной. Требование к адаптеру, в пределах уже принятого (одна SQLite-база, разбор во временное состояние, полная валидация, фиксация только после неё):

    1. провалидировать кандидатное состояние;
    2. сохранить текущее валидированное состояние как backup;
    3. записать внутри одной транзакции;
    4. проверить инварианты и ссылки;
    5. только затем зафиксировать.

    Падение на любом шаге оставляет либо прежнее валидированное состояние, либо новое, но никогда их смесь.

    Backup. Обязателен минимум один сохранённый предыдущий валидированный state. Backup ротируется только из состояния, которое успешно загрузилось и провалидировалось; результат неудачной попытки восстановления в backup не попадает никогда. Сколько копий хранить — вопрос реализации, а не дизайна, и здесь не фиксируется.

    Единицей всего этого остаётся уже принятое разделение профиля (сундук, открытые баблы, потолок Memory, библиотека мозгов, персонажи) и персонажа (уровень, дерево, билд, состояние активного забега). «Поколение профиля» как один неделимый объект не вводится.

    Ревизии мозга в хранилище¶

    Решено. Мозг хранится ревизиями: неизменяемая ревизия с идентификатором, хешем родителя и каноническим хешем содержимого (ревизии мозга). Хранилище обязано удерживать ревизию до миграции наравне с новой — правило «миграция порождает новую ревизию» бессмысленно, если предыдущая затирается ротацией backup.

    Конфликт облачной синхронизации. Если один мозг разошёлся правками на двух устройствах, результатом становятся две именованные сестринские ревизии с общим родителем. Победы последней записи не бывает, автоматического слияния графов не бывает тоже: граф — программа игрока, и объединение двух программ по узлам даёт третью, которую не писал никто. Оба снимка профиля архивируются, ни один не выбрасывается. Выбор между сестринскими ревизиями делает игрок, как и всякий исход из поведения при невалидном сохранении. Технический предел синхронизации прежний: WAL/SHM закрываются до отдачи базы облаку (SQLite в WAL-режиме).

    Экспорт и импорт. Экспорт — атомарный валидированный архив: все ревизии мозга со своими хешами плюс манифест (версии словаря, схемы и контента, состав ревизий и их связи). Импорт валидирует архив целиком до фиксации и создаёт новый профиль или новую ревизию; существующий профиль или существующую ревизию импорт не перезаписывает никогда. Частично импортированного архива не существует — отказ работает так же, как отказ загрузки.

    Кодирование и миграции¶

    Payload начинается с версии кодека и использует unsigned varints вместе с zig-zag encoding знаковых значений роллов. Естественные boolean-состояния разделяют поле флагов uint16. Остальные данные остаются явными: ручная межполевая упаковка по битам намеренно исключена, потому что осложняет миграции и отладку, а overhead строки и индекса базы обычно превышает экономию нескольких байтов.

    Definition ID никогда не переиспользуются: ссылка — пара (namespace, uint32), выведенный из генерации контент сохраняет определение-надгробие, а remap ID после релиза запрещён (жизненный цикл ID контента). Ревизии контента либо сохраняют обратную совместимость, либо мигрируют записи возобновляемыми batch-операциями. Поддержка декодером предыдущей версии сохраняется во время rolling deployment; backfill записывает новую версию и проверяет количество записей и checksums, после чего старое декодирование удаляется отдельным поздним релизом.

    Ёмкость и наблюдаемость¶

    Страницы инвентаря загружаются по индексированному ключу owner/location, а не выборкой всех предметов мира. Batch get сохраняет запрошенный порядок ID среди найденных записей; list pagination использует монотонный item_id, а не offsets. Неизменяемые определения кешируются глобально, небольшие активные инвентари — на сессию.

    Следует измерять transaction latency, conflict rate, payload bytes/item, rows read, idempotency hits и причины ошибок craft/transfer.

    Команды измерения:

    go test ./internal/itemstore
go test -run '^$' -bench BenchmarkCodec -benchmem ./internal/itemstore
go test -run '^$' -bench BenchmarkEncodeMillion -benchtime=1x -benchmem ./internal/itemstore

    Benchmark миллиона предметов намеренно запускается только явно, поскольку создаёт крупную синтетическую fixture. Результаты зависят от машины и записываются в release/performance notes, а не фиксируются как обещания производительности.
