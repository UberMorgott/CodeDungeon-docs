    Как подготовить изменение и передать его без потери контракта?¶

    Эта глава задаёт воспроизводимую среду, обязательный локальный цикл проверки и порядок передачи работы между направлениями Go/симуляция и Godot/клиент.

    Что считается единицей работы?¶

    Единицей работы является одна задача с названным владельцем, ограниченным набором путей, входными контрактами, ожидаемыми артефактами и проверяемым критерием готовности. Задача заканчивается одним логическим изменением: коммит не смешивает авторитетное ядро, представление и независимое обновление инструментария. Если функция требует изменения общего контракта, владелец контракта выпускает его отдельным изменением до кода потребителей.

    Входом рабочего цикла служат актуальная ветка main, задача и канонические главы или схемы, на которые она опирается. Выходом служат проверенный diff, коммит или PR и handoff с фактическими результатами команд. Общий workflow и общие файлы координации принадлежат направлению Go/симуляция; направление Godot/клиент владеет изменениями внутри клиентской зоны и передаёт их через review.

    Работа не расширяется за пределы объявленного scope без новой договорённости. shared/proto/, schema и ID families меняются только их владельцами; потребитель генерирует или импортирует контракт и не создаёт локальную копию полей, opcode, ID или defaults. Wire evolution принадлежит контрактам и потоку данных, content schema и content ID — пакетам контента, а состав и расписание тестовых слоёв — тестированию и CI.

    Состояния задачи идут в одном направлении: подготовлена, реализуется, проверена локально, передана на review, принята. Ошибка проверки возвращает задачу в реализацию; замечание review возвращает её с конкретным path:line и требуемым исправлением. Неизвестный результат команды, пропущенный обязательный gate или незафиксированная версия инструмента не считаются успехом.

    Как подготовить рабочее место?¶

    Команды запускаются из корня репозитория, если раздел не требует перейти в каталог Go module. Требуемые версии задаёт технологический baseline: Go берётся по go.mod, основной клиент открывается Godot 4.7.1.stable.official, а GDScript-инструменты устанавливаются из requirements-tools.txt. Для сборки документации зависимости устанавливаются отдельно из requirements-docs.txt.

    python -m pip install --requirement requirements-tools.txt
python -m pip install --requirement requirements-docs.txt

    Локальный путь к Godot не коммитится. tools/godot.ps1 сначала читает $env:GODOT_BIN, затем ищет godot и godot4 в PATH; отсутствие исполняемого файла завершает команду ошибкой. Wrapper также проверяет наличие project.godot, поэтому ошибочный -Project не должен приводить к запуску другого проекта.

    Основной проект передаётся wrapper явно; codedungeon/ — единственный Godot-проект в репозитории. Расширение VS Code geequlim.godot-tools и editor bridge помогают в интерактивной работе, но их наличие не является условием сборки или CI.

    MCP остаётся необязательным инструментом редактора. Единственная репозиторная конфигурация находится в .mcp.json, Godot bridge запускается через tools/godot-mcp.ps1, а сервер фиксируется как @npgamedev/godot-mcp-server@1.0.0. MCP не заменяет CLI wrappers, не добавляет второй bridge и не записывает в репозиторий machine paths, credentials или локальное состояние редактора.

    Как запускать Godot и проверять его файлы?¶

    Godot запускается только через tools/godot.ps1. tools/check-godot.ps1 является общим интерфейсом проверки проекта: Import выполняет headless import и проверку ресурсов, Smoke запускает один headless-кадр главной сцены, All выполняет оба шага в этом порядке. Локальный полный прогон выглядит так:

    pwsh -File tools/check-godot.ps1 -Mode All -Project codedungeon

    Поведение хранится в .gd, reusable configuration и data — в .tres, композиция сцен — в .tscn. Текстовая правка .tres или .tscn сохраняет resource IDs, ownership, instance overrides, signal connections и typed arrays; GDScript-выражения в сериализованный ресурс не вставляются. Сложная иерархия, анимация, TileMap и массовая пересборка сцены выполняются в редакторе, после чего diff проверяется до запуска импорта.

    Каждый изменённый .tres или .tscn сначала проходит профильный validator. Самодостаточный .gd можно дополнительно разобрать через --check-only; этот шаг не используется как ложный gate для скрипта, которому при загрузке необходим autoload singleton.

    python .agents/skills/godot/scripts/validate_tres.py <path-to-resource.tres>
python .agents/skills/godot/scripts/validate_tscn.py <path-to-scene.tscn>
pwsh -File tools/godot.ps1 -Project codedungeon -GodotArguments @('--headless','--check-only','--script','res://<path-to-script.gd>')

    Ошибка validator, import или smoke останавливает передачу изменения. Разработчик исправляет первичную ошибку, повторяет упавший шаг и только затем запускает последующие. Если Godot или wrapper недоступен, handoff называет отсутствующую prerequisite и перечисляет проверки, которые из-за неё не выполнялись; другая версия движка не подставляется.

    Как форматировать и проверять изменение локально?¶

    Проверки идут от дешёвых и локальных к интеграционным. Первый шаг для любого изменения — git diff --check. Для каждого изменённого GDScript затем выполняются gdformat --check и gdlint; formatter можно запустить без --check на тех же файлах, после чего его diff просматривается вручную.

    requirements-tools.txt фиксирует gdtoolkit==4.5.0. Корневой gdlintrc задаёт max-line-length 120 и читается только при запуске gdlint из корня репозитория. gdformat не читает этот файл и применяет собственный предел 100, поэтому успешный formatter не заменяет lint и наоборот.

    После форматирования выполняются профильные validators ресурсов, допустимый parse check и tools/check-godot.ps1 -Mode All. Для Go-файлов применяется gofmt, затем из каталога module запускается go test ./...; protocol change дополнительно проходит каноническую генерацию и проверки всех потребителей. Для Markdown и mkdocs.yml выполняется строгая сборка сайта.

    git diff --check
gofmt -w <changed-go-files>
go test ./...
mkdocs build --strict

    Единым gate перед коммитом служит tools/check.ps1, который создаётся на S0 и вызывает репозиторные проверки, а не реализует параллельные правила. Его код возврата 0 означает, что применимые проверки завершились успешно; любой другой код блокирует handoff. Точный состав быстрых, merge и nightly gates, детерминированный corpus и contract fixtures принадлежат следующей главе, поэтому здесь они не перечисляются второй раз.

    Generated editor state не является конфигурацией. В diff не попадают .godot/, imported artifacts, builds, export credentials, signing keys, .env, logs, screenshots, local MCP files и machine-specific IDE settings. Реальный секрет не заменяется «временным» коммитом: репозиторий получает только environment placeholder или .env.example без значения.

    Что именно повторяет CI?¶

    Godot workflow устанавливает Python toolchain, gdtoolkit==4.5.0 и Godot 4.7.1. Проверяются изменённые файлы Stage-1-пути клиента — codedungeon/scripts/{boot,ipc,generated}/** и codedungeon/scripts/autoload/state_bridge.gd — плюс любой вновь добавленный .gd где угодно; дострадийный остров удалён, поэтому этими путями codedungeon/scripts сегодня и исчерпывается. Для этого набора он выполняет gdformat --check и gdlint, затем запускает tools/check-godot.ps1 -Mode Import. Smoke остаётся обязательной локальной проверкой через -Mode All, даже если отдельный CI job его не вызывает.

    Documentation workflow устанавливает requirements-docs.txt и выполняет mkdocs build --strict на PR и на изменении документации в main. Публикуется только сгенерированный каталог сайта; он не редактируется вручную и не становится источником Markdown. Ошибка navigation, link resolution или strict build блокирует публикацию так же, как ошибка компиляции блокирует код.

    Локальный зелёный результат не подменяет CI, потому что CI подтверждает pins и чистое окружение. CI также не исправляет файлы, не обновляет golden data и не принимает изменение контракта автоматически. Toolchain, action или engine version обновляются отдельным PR вместе с pins, wrappers и workflow; такое изменение проходит отрицательные примеры gate и все затронутые проверки до использования новой версии в feature work.

    Как два направления передают работу друг другу?¶

    Направление Go/симуляция ведёт общие contracts, tools/, .github/workflows/, CODEOWNERS, mkdocs.yml и изменения документации, затрагивающие общий порядок. Оно делает по одному логическому коммиту непосредственно в main и обязано до отправки пройти тот же локальный gate. Направление Godot/клиент работает в короткой ветке feat/<screen-name> или столь же узкого назначения, открывает PR и не держит ветку после того, как её scope принят или отменён.

    Godot/клиент не изменяет ядро, schema, published content или замороженные UI fixtures ради прохождения своего экрана. Если клиенту не хватает поля или fixture, он передаёт владельцу минимальный запрос к контракту и ждёт отдельного schema-first изменения. Экран считается подключённым только тогда, когда прежняя fixture и реальные данные используют один view-model contract без правки layout ради интеграции.

    В docs/ пишет один человек за раз. Изменения общих файлов заранее резервируются у направления Go/симуляция, чтобы два PR не создавали конкурирующие источники истины. Review проверяет только заявленный diff и его контракты; замечание содержит путь, строку, серьёзность, дефект и ожидаемое исправление.

    Handoff помещается в завершающее сообщение и содержит: краткий результат, затронутые пути, выполненные команды с фактическим итогом, пропущенные проверки с причиной, сделанные допущения и оставшийся риск. Сырой многостраничный вывод не заменяет итог, но точная ошибка и exit code сохраняются для неуспешного шага. PR направления Godot/клиент сливается направлением Go/симуляция только после зелёного CI и закрытых замечаний.

    Как необязательно подключать coding agents?¶

    Agent dispatch использует тот же контракт задачи и не ослабляет review. В spec указываются role, scope, источники, артефакты, критерии готовности, обязательные команды и пути, которых нельзя касаться. Одна задача получает один child worktree и одну короткую ветку; параллельные задачи допускаются только при непересекающихся файлах и независимых контрактах.

    orca orchestration run-create --objective "<milestone>" --json
orca orchestration task-create --task-title "<title>" --spec "Role: <role>. Scope: <paths>. DoD: <checks>." --json
orca orchestration worker-start --task <task_id> --agent <agent> --worktree new-child --name <branch> --json
orca orchestration check --json
orca orchestration worker-read --dispatch <dispatch_id> --json
orca orchestration worker-release --dispatch <dispatch_id> --json

    Исполнитель сначала читает AGENTS.md и названные в spec канонические документы. Reviewer работает только на чтение и не расширяет scope; код одного agent family проверяет другой. Tester перед Go-прогоном выполняет go clean -testcache, затем приводит фактический результат go test ./...; отчёт исполнителя помещается в тело завершающего worker_done, а не отправляется отдельным сообщением, которое может потеряться при закрытии dispatch.

    Выбор конкретной модели и reasoning effort является параметром запуска, а не контрактом репозитория. Отсутствие orchestration или MCP не блокирует ручную работу: человек выполняет те же команды, создаёт тот же diff и передаёт тот же handoff. Результат агента не принимается по заявлению исполнителя без локального gate, CI и review.

    Как обновляется граф знаний по документации?¶

    graphify-out/ держит граф знаний по docs/ и обновляется сам: tools/install-git-hooks.ps1 ставит post-commit, который отсоединённо запускает tools/graph-refresh.ps1, поэтому коммит не ждёт пересборку и не падает на её ошибке. Скрипт сверяет файлы с graphify-out/manifest.json, при отсутствии изменений печатает graph up to date и выходит; изменённый код разбирается детерминированным AST, изменённые документы уходят чанками в claude -p --model claude-opus-4-6 по контракту извлечения graphify с доступом только на чтение — без интерактивного агента. Дальше идут build, clustering, отчёт и экспорт; манифест сохраняется только после фактической записи графа, .refresh.lock не даёт двум коммитам подряд столкнуться, итог каждого прогона дописывается в graphify-out/refresh.log. Полная пересборка в обход манифеста — tools/graph-refresh.ps1 -Force.

    Что нужно сделать¶

    • Владелец: Go/симуляция, этап S0 плана производства. Направление Godot/клиент является обязательным потребителем workflow и владеет исполнением клиентских проверок в своих задачах; правила применяются на всех последующих этапах.
    • Артефакты: AGENTS.md как единая точка входа для агентов; go.mod; requirements-tools.txt, requirements-docs.txt, gdlintrc; tools/check.ps1, tools/godot.ps1, tools/check-godot.ps1, tools/godot-mcp.ps1; .github/workflows/ и CODEOWNERS; .vscode/extensions.json; корневая .mcp.json; короткие ветки и handoff template с результатами проверок.
    • Готово, когда: новая машина с заявленными prerequisites устанавливает зависимости только из repository manifests; wrappers находят ровно Godot 4.7.1, отклоняют отсутствующий проект и возвращают ненулевой код при ошибке; tools/check.ps1 проходит на чистом дереве и падает на отрицательных примерах S0; изменённые .gd, .tres и .tscn проходят свой полный порядок; Go test cache очищается перед независимым тестовым handoff; mkdocs build --strict проходит; PR Godot/клиента содержит ограниченный diff, фактические результаты и зелёный CI; общая schema меняется отдельным owner-controlled коммитом до потребителя.
