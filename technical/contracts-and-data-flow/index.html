    Как команды, события и данные переходят между Go и Godot?¶

    Эта глава задаёт единый wire-контракт двух процессов: направление команд и событий, framing, versioned envelope, правила эволюции Protobuf и владельцев долговечных данных.

    Реализует: авторитетный расчёт и показ готового боя, разбор законченной записи.

    Где проходит граница данных?¶

    Godot создаёт намерение из ввода игрока, но не создаёт игровой факт. Намерение содержит стабильные ID и только ту конфигурацию, которую разрешает соответствующий application contract. Go принимает команду, проверяет её, упорядочивает относительно других принятых команд и единолично изменяет состояние профиля, забега или симуляции.

    Обратный поток состоит из результата команды, подтверждённых snapshots и доменных либо presentation events. Клиентский store применяет их как read-only проекцию и уведомляет сцены; сцена не меняет золото, HP, карту, предмет, прогрессию или результат боя напрямую. Потерянную проекцию можно восстановить из нового snapshot, поэтому она не используется как save, replay или источник восстановления Go.

    Godot input -> command facade -> GameTransport -> Go protocol adapter
                                                     |
                                                     v
                                             application handler
                                                     |
                                      authoritative state transition
                                                     |
                                                     v
Godot scene <- client store <- DTO mapper <- result / snapshot / event

    Схема показывает нормативное направление вызовов, но не является wire-схемой. Transport adapter не импортируется доменными пакетами, а DTO mapper не присваивает Protobuf-сообщению gameplay-смысл, которого нет в результате application handler.

    Для боя действует более узкий выходной контракт: Go сначала полностью завершает симуляцию и фиксирует законченную запись событий, затем передаёт её для показа. Частота кадров, буфер представления, пауза, seek и скорость playback не посылают команд обратно в симуляцию и не меняют уже рассчитанный результат. Состав replay container и его совместимость принадлежат главе о replay, а порядок тиков и событий — ядру симуляции.

    Как проходит одна команда?¶

    Command facade в Godot создаёт команду только из доступной операции UI. Команда получает request_id; после создания этот идентификатор не меняется при безопасном повторе. Если операция относится к уже открытой сессии, она несёт выданный Go session_id, а доменные revision и stable ID добавляются только там, где этого требует контракт владельца состояния.

    Protocol adapter проверяет token текущего запуска, envelope, допустимый размер, opcode и ProtoJSON до вызова application handler. Handler преобразует DTO в доменную команду, заново проверяет права, фазу и входные ID, затем канонизирует и упорядочивает вход. Только после этих шагов команда может изменить авторитетное состояние или запустить детерминированную операцию.

    Каждая принятая команда получает ровно один типизированный outcome. Успех подтверждает уже применённое изменение и может сопровождаться snapshot или событиями; отказ содержит machine-readable причину и не меняет состояние. Повтор того же request_id не применяет изменение второй раз и возвращает тот же наблюдаемый outcome либо его эквивалентную подтверждённую проекцию.

    sequence позволяет обеим сторонам обнаружить пропуск, повтор и нарушение порядка. Go остаётся владельцем порядка применения входных команд, а Godot применяет подтверждённые выходы не более одного раза и только в порядке серверного потока. При разрыве связи клиент запрашивает актуальную проекцию и не пытается заполнить пропуск самостоятельно.

    Счётчик ведётся каждым направлением отдельно и на каждое соединение: первое сообщение клиента несёт 1, каждое следующее — ровно предыдущее + 1; серверное направление нумеруется своим счётчиком тем же правилом. Входящий конверт с любым другим значением — дубликат, пропуск или перестановка — отклоняется типизированной ошибкой до вызова handler, поэтому команда не может примениться второй раз или не в свою очередь. Сброса счётчика посреди сессии не существует; новое поколение начинается только с новым соединением.

    Ошибка framing, распаковки, JSON mapping, неизвестный opcode, превышение лимита или невалидный envelope останавливает сообщение до доменного handler. Если request_id уже безопасно прочитан, отказ коррелируется с ним; иначе transport выдаёт диагностическую ошибку соединения. Ни одна такая ошибка не оставляет частично применённую команду и не заставляет Godot вычислять предполагаемый результат.

    Как устроены frame и envelope?¶

    MVP использует binary WebSocket frame. Первые два байта содержат uint16 opcode в little-endian, оставшаяся часть содержит gzip-сжатый ProtoJSON UTF-8. После распаковки payload интерпретируется только как Protobuf message, назначенный этому opcode; произвольный JSON не является вторым публичным контрактом.

    Opcode объявляется в канонической Protobuf-схеме ровно один раз и не повторяется ни списком констант в Go и GDScript, ни enum'ом внутри самой схемы. Конкретно: uint16 opcode есть номер поля заполненного члена oneof Envelope.payload, и Go читает его через protoreflect, а не через собственную таблицу констант. Параллельный enum со списком opcode запрещён: он не проверяется ни одним из кодеков и потому способен разойтись со схемой, не вызвав отказа в runtime. Отсюда два правила приёма: opcode, не соответствующий ни одному объявленному полю payload, отклоняется до распаковки, а конверт, чей заполненный payload не совпал с opcode заголовка, отклоняется после разбора. Generated Go types и проверяемый Godot codec получают одно и то же сопоставление из schema/tooling. Domain handler не видит opcode, WebSocket frame или gzip: protocol adapter выбирает тип команды и вызывает типизированный application port.

    Versioned envelope несёт следующие обязательные значения безотносительно конкретного payload:

    Значение Кто задаёт Наблюдаемый контракт
    protocol_version поставляемая версия отправителя получатель использует только явно поддерживаемую версию wire-семантики
    request_id инициатор команды повтор команды распознаётся как тот же запрос; result коррелируется с запросом
    session_id Go после создания сессии сообщение другой или уже закрытой сессии не достигает доменного изменения
    sequence отправитель для своего направления потока пропуск, повтор и перестановка обнаруживаются до применения потребителем
    content_hash Go из загруженного immutable package; Godot отражает согласованное значение команда и выход относятся к одному snapshot контента

    Точные Protobuf message names, field numbers, oneof payload и enum values живут только в shared/proto/. Markdown фиксирует их семантику и evolution rules, но не создаёт копию схемы. Лимиты frame и decompressed payload задаются transport-конфигурацией и проверяются симметрично Go и Godot; неизвестное числовое значение нельзя подменять локальным default. Лимит записи (таймаут одной синхронной отправки) принадлежит только Go: очереди конвертов нет ни на одной стороне.

    Когда соединение готово к gameplay-командам?¶

    Go создаёт случайные endpoint и token для каждого запуска по контракту топологии runtime. После установления WebSocket обе стороны завершают compatibility handshake: token относится к текущему поколению процесса, protocol_version поддерживается обоими участниками, а content_hash совпадает с пакетом, который Go уже загрузил для сессии. До выполнения всех условий соединение не переходит в ready и gameplay-команды не принимаются.

    Рукопожатие состоит ровно из четырёх сообщений и заканчивается четвёртым. Последнее сообщение идёт от Go и несёт весь набор значений, которыми Go владеет на этом этапе; отдельного запроса за теми же значениями после него нет. Клиент переходит в ready прямо на этом сообщении и показывает полученные числа, не изобретая ни одного из них. Значение, уже выданное в этом снимке, не получает второго wire-представления: дублирующее сообщение не добавляет ни аутентификации, ни согласования версии или контента.

    Несовместимость не скрывается частичным чтением ProtoJSON. Клиент получает типизированную диагностическую причину, не строит подтверждённую проекцию и не повторяет запрос с догадкой о другой версии. Точный порядок сообщений negotiation и переходов handshake берётся из записи «Как устроено рукопожатие между Godot и побочным процессом ядра?»; launcher, Boot/Connection screen и transport не задают каждый свою последовательность.

    Первое сообщение рукопожатия не может быть привязано к выбранной версии: именно оно предлагает список, из которого выбирают. Клиент штампует на нём свой максимум, поэтому клиент с поддержкой [1,2] придёт к ядру версии 1 с внешним значением 2. Правило bootstrap: внешний protocol_version первого сообщения проверяется не на равенство версии ядра, а на принадлежность списку supported_protocol_versions того же сообщения; общая версия затем ищется как пересечение, и отсутствие пересечения — единственный повод отказать. Все конверты после ServerHello привязаны к выбранной версии в обе стороны. Обратное правило (сверять внешнее значение с версией ядра сразу) отвергло бы двух собеседников, у которых общая версия есть, и обессмыслило бы само поле.

    Проверка версий не заканчивается рукопожатием. Команда, пришедшая в состоянии ready, заново сверяет не только session_id, но и protocol_version и content_hash: рукопожатие договорилось об одной wire-версии и одном снимке контента, и сообщение, переставшее их нести, в эту договорённость не входит и до handler не доходит. Каждое из трёх несовпадений даёт собственную типизированную причину отказа.

    Повторное подключение снова проходит authentication и compatibility gate. Оно может восстановить существующую авторитетную сессию только по данным Go; client snapshot, сохранённый envelope или token прошлого запуска для этого не подходят. Изменение content_hash не переключает уже открытую сессию на другой пакет.

    Как эволюционирует Protobuf?¶

    shared/proto/ является единственным источником wire-visible messages, enum и opcode. Схемы разделяются по bounded context и получают версию в package name. Generated code создаётся из этих файлов и не редактируется вручную; Godot mapping проверяется тем же набором golden fixtures. Пакеты codedungeon.ipc.v1 генерируются в server/internal/gen/ipcv1/ намеренно: сгенерированный код не является публичным API сервера, и internal/ запрещает импорт его извне модуля средствами самого Go. Генерацию выполняет только buf по shared/buf.gen.yaml; второго генератора и второй выходной директории нет.

    Совместимое расширение внутри одной package version добавляет новое поле с новым номером или новое enum value, если старый потребитель способен сохранить прежний смысл. Номер поля никогда не переиспользуется. Удалённые имя и номер резервируются, существующий тип и смысл поля не меняются, а нулевое enum value остаётся нейтральным UNSPECIFIED-состоянием.

    Изменение типа, смысла, структуры обязательного выбора или JSON mapping является breaking change и создаёт новую package version. Один message не несёт два несовместимых смысла. Каждая поддерживаемая версия получает изолированный adapter в текущую application command; домен не ветвится по opcode или версии wire.

    ProtoJSON требует отдельной проверки совместимости, потому что Godot читает JSON names и enum representation, а не generated binary codec. Для каждого изменения schema fixtures доказывают одинаковое чтение Go и Godot, поведение неизвестного совместимого поля, отказ на неизвестной обязательной семантике, границы чисел и точное сопоставление enum. Buf format, lint, breaking и generated-diff checks входят в gate изменения схемы.

    protocol_version описывает совместимость envelope и маршрутизации, но не заменяет версии доменных данных. content_hash закрепляет определения и баланс; save schema version принадлежит persistence; replay schema и simulation compatibility принадлежат replay и simulation core. Увеличение одной из этих версий не разрешает молча преобразовать остальные.

    Кто владеет content, save и replay?¶

    Класс данных Канонический владелец Вход и выход Инвариант и отказ
    Immutable content package пакеты контента, загружает Go строгий JSON и JSON Schema превращаются в read-only snapshot с version/hash пакет не содержит player state; ошибка schema, ID или hash запрещает загрузку
    Player save и состояние забега persistence, Go persistence adapter domain repositories читают и транзакционно пишут SQLite WAL Godot не открывает БД; ошибка записи не создаёт частичный state
    Replay replay, Go replay writer/store завершённая симуляция выпускает авторитетную запись; reader отдаёт presentation events replay не начисляет награды и не заменяется seed-пересчётом на клиенте
    Client projection архитектура клиента, Godot store snapshots и events обновляют view-model и сигналы экранов проекция восстанавливаема, не сохраняется обратно как игровая истина
    UI fixtures Go/симуляция создаёт, Godot/клиент читает fixtures/ui/ поставляет замороженные view-model и записи для экранов клиент не переписывает fixture ради прохождения собственной приёмки

    Wire protocol переносит эти данные, но не становится их владельцем. Protobuf DTO не заменяет content definition, SQLite record или replay container только потому, что похожие значения проходят по соединению. Между форматом владельца и DTO всегда находится явный adapter, а версия и ошибка остаются в области исходного владельца.

    Что нужно сделать¶

    • Владелец: направление Go/симуляция владеет wire schema, opcode, envelope semantics, version policy, ordering, idempotency и protocol fixtures. Схема и fixtures замораживаются на S0. Live WebSocket и handshake жизненного цикла реализованы досрочно как сквозной срез Stage 1 вместо запланированного S9, чтобы топология проверялась раньше детерминизма; codec, DTO mapper и применение выходного потока живут на стороне Godot без присвоения контракта. Остальные opcode и gameplay-команды приходят по плану производства.
    • Артефакты: versioned .proto packages в shared/proto/; shared/buf.yaml и shared/buf.gen.yaml; generated Go package server/internal/gen/ipcv1/; framing и protocol adapters в server/internal/ipc/; client transport в codedungeon/scripts/ipc/ и DTO mapper с применением состояния в codedungeon/scripts/autoload/state_bridge.gd; замороженные fixtures/ui/; Go ↔ Godot golden fixtures для каждого opcode, envelope outcome и ошибки совместимости.
    • Готово, когда: Buf format/lint/breaking и generated-diff gates проходят; каждый opcode декодируется обеими сторонами в одинаковый смысл; malformed, oversized и неизвестный frame не меняет domain state; duplicate request_id не повторяет изменение; sequence gap или перестановка не меняют исход; неверные token, protocol_version или content_hash не переводят соединение в ready и дают диагностируемый отказ; reconnect восстанавливает проекцию без клиентского state upload; завершённый бой воспроизводится из переданной записи, а управление playback не меняет канонический результат.
    • Не трогать: endpoint, token generation, heartbeat и process lifecycle принадлежат runtime-topology.md; tick order, fixed point, RNG и event ordering — simulation-core.md; replay container, codec, seek и retention — replay.md; JSON Schema, content IDs и package publication — content-packages.md; SQLite tables, migrations и recovery — persistence.md; reducers, scene state и navigation — client-architecture.md; удалённая сеть и Online — future-online.md.
