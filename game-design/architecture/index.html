    Архитектурный скелет¶

    Этот документ задаёт границы владения и контракты, по которым несколько команд могут параллельно собирать CodeDungeon. Он не заменяет тематический GDD: если здесь и в тематическом документе различается gameplay-правило, источником истины остаётся тематический документ.

    Выбранные реализации этих границ, их текущий статус и условия пересмотра описаны в технологическом стеке. Архитектурный скелет остаётся владельцем контрактов подсистем; технический документ не создаёт вторую копию gameplay-правил.

    Граница MVP¶

    Подтверждено. MVP делает параллельно весь solo-контент: забег, крафт, пассивное дерево и прогрессию. Сеть, PvP, рынок и co-op отложены. Владелец проекта принял риск параллельной сборки нескольких систем.

    Подтверждено. Godot — только слой представления. Он владеет состоянием UI, вводом, настройками, локализацией, интерполяцией анимации, воспроизведением replay и косметическим ragdoll. Go владеет всей игровой истиной: правилами, состоянием, данными и симуляцией. Godot никогда не отправляет в Go transform, контакты, состояние анимации или результаты ragdoll — только намерения и конфигурацию. Поток односторонний.

    Подтверждено. Полная физическая симуляция боя вырезана из MVP; бой — простая строго детерминированная логическая симуляция. См. симуляцию боя и запись боя и спецификацию боевой симуляции.

    Подтверждено. Игра запускается двумя процессами ОС: Go launcher/core (точка входа Steam, владеет SQLite, контентом и симуляцией) и клиент Godot. Headless-worker Godot вырезан: после выреза физики боя исполнять ему нечего. Контракт описан в топологии процессов.

    Подтверждено. Co-op отложен за пределы MVP окончательно. MVP — чистое solo, сетевого кода в нём нет вообще.

    С чего начинается разработка¶

    Подтверждено. Первый шаг реализации — ядро симуляции на Go вместе с его тестами: тиковый цикл, фиксированная точка, окружности, действия, события. Графики нет; корректность проверяется хешами детерминированного прогона. Канонический порядок стадий тика, контракты PCG32 и фиксированной точки заданы в спецификации боевой симуляции.

    Всё остальное идёт после того, как ядро умеет провести бой headless и воспроизвести его: загрузчик контента, редактор мозга, клиент. Порядок предпосылок ниже («Что можно разрабатывать параллельно») действует уже поверх работающего ядра.

    Как читать статусы¶

    • CURRENT — prototype: граница уже видна в коде, но может быть временной или неполной.
    • TARGET: обязательная целевая граница.
    • MIGRATION SEAM: совместимый шов, через который прототип заменяется без одновременной переделки всей игры.

    Главный инвариант: авторитетный Go core единолично владеет игровыми данными и решениями. Godot отправляет намерения со стабильными ID и отображает подтверждённое core состояние; он не рассчитывает исход боя, награды, характеристики, доступность контента или прогрессию. В MVP solo Godot запускает упакованный локальный server-sidecar; в отложенном приватном co-op тот же core будет авторитетен на машине host. Симуляция боя строго детерминирована: одинаковые входы дают побитово одинаковый результат и однозначный порядок событий внутри тика. Replay воспроизводит запись и регенерирует решения ИИ из seed, а не пересчитывает бой по другим правилам. Эта граница также не является защитой от владельца машины и не обещает античит.

    Core не привязан к топологии развёртывания. MVP использует только локальный профиль для solo; player-hosted профиль co-op, LAN, Steam и иные способы соединения подключаются транспортными адаптерами уже после MVP. Будущий Online разворачивает тот же gameplay/application core в доверенной удалённой среде и добавляет удалённые identity, persistence, matchmaking и operations-адаптеры. Offline- и Online-персонажи образуют разные realm’ы: перенос локальных результатов, предметов или силы в доверенный Online запрещён.

    Карта зависимостей¶

    На схеме вызовов A -> B всегда означает: A вызывает публичный контракт B. Это направление compile-time/application dependency, а не владение данными.

    Godot UI -> Client state store -> Client transport -> Versioned protocol adapter
                                                        |
                                                        v
                                               Application handlers
                                                        |
                                                        v
                                           Session & Party assembly
                                                /              \
                                               v                v
                                      Identity/Profile port   Run/Mission/Arena orchestrator
                                                              |
                 +----------------+---------------------+------------------+
                 v                v                     v                  v
       Dungeon generator    Build resolver      Item/Progression     Combat simulation
                                  |                     |              /    |     \
                                  v                     v             v     v      v
                          AI validator/executor   Persistence ports   AI  Formula  Content

Balance editor -> Package validation/simulation -> Package publisher
Dungeon / Build / Items / Progression / Combat / AI / Formula -> Immutable content package API

    Последняя стрелка свёрнуто показывает, что runtime-подсистемы читают определения только через API immutable content package. Они не импортируют редактор или publisher; publisher создаёт новую версию пакета, но не меняет уже загруженную.

    Потоки событий и сохранённых данных показаны отдельно: здесь A ~> B означает публикацию, запись или чтение данных, а не compile-time dependency и не вызов владельца обратно из источника.

    Combat simulation ~> Replay writer/store ~> Replay reader
Session / Run / Combat / Economy / Validation ~> Event sink ~> Telemetry & monitoring
Critical account/economy audit events ~> Transactional outbox ~> Audit consumers

    Нижний вызываемый слой не импортирует вызывающий. Подсистемы не читают чужие таблицы, хранилища или внутренние структуры напрямую: запрос проходит через типизированный порт. Транспорт, база данных и UI — адаптеры на краях, а не владельцы доменной логики.

    Подсистемы и контракты¶

    Режимы, сессии и подбор участников¶

    TARGET. Владеет: типом режима, составом и жизненным циклом сессии, готовностью участников, результатом матча и правилами подключения. Offline поддерживает roguelike-забеги и фиксированные миссии в solo и private co-op; PvP — отдельный матч на арене без карты забега и миссий. Online PvE не запускает roguelike: PartyAssembler до старта формирует отряд для линейной серии боёв на истощение, а Matchmaker после заданного времени может заполнить пустые слоты серверными ботами примерно средней силы людей в отряде. После старта состав закрыт для новых участников. Размеры групп, порог ожидания, PvP-правила и награды здесь намеренно не определены.

    Online-сессия сохраняет занятый человеком party slot после disconnect: персонаж продолжает бой с последним серверно-валидированным Brain, а отключение само по себе не ставит сессию на паузу и не завершает её. SessionResumeStore связывает аутентифицированный reconnect с тем же slot/character; это восстановление прежнего участника, а не mid-session join.

    Обещает: создать неизменяемый SessionDescriptor с mode/content-version/participant IDs; выдавать оркестратору только допустимые команды перехода; завершить сессию ровно один раз. Требует: идентичности игроков от profile-порта, совместимой версии контента и результата авторитетной симуляции. Запрещено: комнате, клиенту или бою самостоятельно добавлять участника, менять режим либо определять награду.

    CURRENT — prototype: server/internal/room объединяет комнату, готовность, карту, билды, золото, HP, офферы и прогрессию; server/internal/game/handler.go маршрутизирует команды и запускает симуляцию. Это полезный вертикальный срез, но не целевая граница multiplayer.

    MIGRATION SEAM: ввести интерфейсы PartyAssembler, SessionStore и ModeRules, сначала адаптировав к ним существующий room.Manager; будущий Matchmaker реализует PartyAssembler, не меняя оркестраторы. GDD: основной цикл и режимы, видение.

    Оркестратор забега, миссии и арены¶

    TARGET. Владеет: серверной машиной состояний конкретного прохождения, seed, картой и посещёнными узлами Offline roguelike-забега, очередью боёв линейного режима, идентификатором миссии/арены, переходами и применением подтверждённых результатов. Это единственное место, которое связывает бой, награду и следующий шаг режима. Online PvE выбирает из versioned content последовательность обычных боёв и боссов, но не создаёт MapDefinition/RunMapState и не вызывает контракты выбора узла, торговца или сервисной комнаты.

    В фиксированном Online-межкомнатном состоянии оркестратор единолично владеет дедлайном, обратным отсчётом и голосами за досрочный переход. По дедлайну он переводит отряд дальше независимо от присутствия игроков. Досрочный переход требует подтверждения каждого закреплённого party slot: бот голосует автоматически, а отключённый человек не получает автоматического голоса и потому блокирует только fast skip. Голос является идемпотентной session-командой, а Godot лишь отправляет намерение и отображает серверные timer/vote snapshots.

    В том же состоянии оркестратор запрашивает у item subsystem атомарный absent-loot claim: существующие стаки принимают одинаковые ресурсы, затем забираются все физически помещающиеся предметы. Непоместившийся overflow остаётся unclaimed и forfeited при авторитетном переходе дальше; он не блокирует машину состояний. Run orchestration задаёт момент закрытия окна, а item subsystem единолично решает вместимость и изменение рюкзака.

    Обещает: детерминированные команды StartEncounter, ApplyEncounterResult, ChooseNode для solo, CastNodeVote и авторитетное CloseNodeBallot для co-op, CastIntermissionSkipVote, ClaimOffer, FinishRun; снимок состояния для клиента; идемпотентность команд по request ID. В Offline co-op оркестратор принимает от каждого подключённого участника один голос только за доступный следующий узел, выбирает большинство, а при ничьей использует серверную случайность только между лидирующими вариантами; вся группа получает один зафиксированный переход. Рисование на карте и метки остаются отдельным координационным контрактом и не могут попасть в подсчёт голосов. Тайм-аут и поведение при отсутствии голоса в Offline-маршруте должны быть заданы отдельной версионируемой политикой до реализации, поскольку GDD пока их не определяет. Требует: правила режима, content package, серверные clock/timer ports, сервис боя и доменные порты предметов/прогрессии. Запрещено: обработчику сети напрямую начислять золото, двигать карту, менять HP или закрывать голосование на основании клиентского состояния; клиенту — продлевать дедлайн, засчитывать голос за чужой слот или самостоятельно начинать следующую комнату.

    CURRENT — prototype: эти обязанности распределены между game.Handler, room.Room, dungeon и loot. MIGRATION SEAM: существующие opcode сначала вызывают новый application-service, а ответы остаются прежними до миграции протокола. GDD: основной цикл и забеги, прогрессия и idle.

    Генерация подземелья и шаблоны узлов¶

    TARGET. Владеет: алгоритмами генерации, immutable-шаблонами карт и комнат, стабильными типами узлов и проверкой топологии. Генератор создаёт описание карты, но не владеет состоянием конкретного забега. Оркестратор забега единолично владеет сгенерированным экземпляром карты, текущим и посещёнными узлами, доступными переходами и сделанным выбором пути.

    Обещает: GenerateMap(seed, modeRules, contentVersion) -> MapDefinition; одинаковые входы дают одинаковую карту; результат содержит только валидные stable node/template IDs и проходит topology validation. Требует: правила режима и read-only definitions указанной версии content package. Запрещено: генератору отмечать узел пройденным, выбирать путь, начислять награду или запускать encounter; оркестратору — создавать типы узлов и обходить генератор прямым чтением его шаблонов.

    CURRENT — prototype: server/internal/dungeon/generator.go и templates.go предоставляют детерминированные функции генерации и размера комнаты, но server/internal/game/handler.go вызывает их напрямую, а экземпляр карты хранится в room.Room. MIGRATION SEAM: обернуть текущий dungeon.Generate портом DungeonGenerator, ввести отдельные MapDefinition и RunMapState, затем переключить handler на оркестратор без изменения legacy-ответа FloorMap. GDD: карта, типы узлов и необратимый выбор пути, системный гейтинг контента.

    Бой и действия¶

    TARGET. Владеет: временем симуляции, сущностями боя, фазами действий, ресурсами внутри встречи, положением, эффектами, попаданиями и итогом encounter. Внешний код не меняет HP или action state.

    Обещает: принять валидированный immutable EncounterSpec и вернуть EncounterResult плюс упорядоченный поток событий. Seed и версии входов полностью задают результат: симуляция логическая, целочисленная и строго детерминированная, физика тел в неё не входит. Замороженные параметры, состав событий и RNG описаны в спецификации боевой симуляции. Контракт встречи поддерживает симметричные factions, проверку допустимости цели и ModeRules, не зашивая предположение «игрок всегда атакует монстра». Требует: разрешённый core build, канонические формулы/модификаторы, AI executor, версию контента и версию правил режима. Запрещено: UI управлять паузой симуляции или пересчитывать исход; режиму проникать во внутренний tick-loop; добавлять разбросанные ветви if PvP вместо правил режима; вносить в симуляцию float или зависимость от порядка итерации map.

    CURRENT — prototype: server/internal/game/simulator.go содержит значительную часть боя, а server/internal/combatformula уже выделяет центральный formula engine; клиент проигрывает snapshots. MIGRATION SEAM: Simulator зависит только от интерфейсов formula/AI/content, после чего старые локальные расчёты удаляются по contract-тестам. GDD: бой и действия, симуляция боя и запись боя.

    AI Brain и валидатор¶

    TARGET. Владеет: канонической схемой blueprint, каталогом узлов и портов, Memory-бюджетом, компиляцией/валидацией графа, планированием, interrupts, диагностикой решений и контрактом обмена BlueprintExchange. Редактор владеет только черновым расположением элементов интерфейса.

    Обещает: ValidateBlueprint, CompileBlueprint, ImportBlueprint, ExportBlueprint, Decide и стабильные machine-readable ошибки; versioned declarative envelope со schema/content version, stable IDs, явными миграциями и детерминированным каноническим представлением там, где порядок незначим; никогда не исполнять невалидный graph. Внутриигровая библиотека, строка для clipboard и переносимый файл используют один codec и validator. Требует: серверный каталог навыков/тегов, entitlements прогрессии и read-only combat perception. Запрещено: клиентскому валидатору быть последней инстанцией или определять gameplay-семантику узла; импорту — содержать исполняемый код, файловые пути/ссылки, секреты, произвольные payload’ы или данные прогресса и силы.

    Любой импорт является недоверенным: применяются лимиты размера/глубины/числа элементов, schema/type/ID/edge validation, общий graph/build validator и проверки entitlement/content compatibility. Числовые лимиты и точный codec откладываются до реализации. Blueprint переносит только layout/config алгоритма, поэтому Offline → Online разрешён, но Online core повторяет все проверки авторитетно; предметы, валюты, XP, passive points, Memory, entitlements и power через эту границу не проходят.

    CURRENT — prototype: реализация сосредоточена в server/internal/ai; Godot содержит редактор, реестры и UI-валидацию. MIGRATION SEAM: общий versioned schema/fixtures и cross-client contract-тесты отделяют UX-проверки от авторитетной серверной проверки. GDD: мозг персонажа.

    Канонические теги, формулы и модификаторы¶

    TARGET. Владеет: стабильными tag ID и их категориями, атрибутами, порядком стадий вычисления, stacking/rounding/caps, conversion и форматом modifier. Это общий math kernel для боя, билдов, предметов, навыков и предпросмотра баланса. Нормативный контракт — девять стадий единого конвейера расчёта; отдельных формул урона и митигации нет, три профиля смягчения являются параметрами стадии 6. Порядок операций, округление и caps детерминированы и одинаковы для PvE/PvP; различия задаёт versioned ModeRules, а не отдельные формулы по вызывающим системам. Финальные числовые значения PvP-баланса отложены.

    Обещает: типизированные Evaluate(context, modifiers) и trace результата; валидацию неизвестных ID и запрещённых комбинаций; одну и ту же реализацию для runtime и balance simulation. Требует: только immutable registries из content package. Запрещено: произвольным системам вводить string-key формулы или собственный порядок применения эффектов.

    CURRENT — prototype: server/internal/combatformula — начало целевой границы, но формулы также живут в simulator и legacy loot; часть параметров передаётся через строки и interface{}. MIGRATION SEAM: characterisation-тесты фиксируют текущее поведение, адаптер переводит legacy modifier в канонический тип, затем старые ветви удаляются. GDD: навыки и теги, пассивное дерево, предметы и крафт.

    Предметы, инвентарь, крафт и хранение¶

    TARGET. Владеет: экземплярами предметов, их revision/owner/location/realm, инвентарём и экипировкой, атомарными рецептами и сохранением. itemization владеет правилами генерации/мутации предмета; repository владеет только надёжной записью, но не правилами. В будущем Online отдельный авторитетный marketplace application service единолично владеет жизненным циклом лота, допустимыми BuyIntent, выбором победителя и межигровой сменой владельца по правилам из предметов и крафта. Item store остаётся источником истины об экземпляре и владельце, Economy wallet/ledger — о доступных и зарезервированных балансах торговых валют; marketplace координирует их одной транзакцией, но не присваивает их данные себе. Каноническое определение валюты задаёт её торговость и допустимость как материала крафта.

    Обещает: ID-based query и атомарные команды equip/craft/move с optimistic revision; результат операции либо целиком сохранён, либо не применён. Online marketplace атомарно и идемпотентно проводит расчёт, а stale-клиент всегда повторно валидируется сервером; oversell невозможен. Прямой Online-transfer между игроками не существует. Offline/private co-op использует отдельный session-scoped direct-transfer contract для предметов и ресурсов между участниками текущей сессии; его недоверенные результаты не принимаются Online. Требует: content registry, formula kernel, realm + character/profile ID, authoritative clock, wallet reservation port, transaction/outbox, audit log и persistence port. Запрещено: run, UI или transport напрямую менять лот, победителя, владельца, аффикс, баланс/резерв кошелька, слот, relist lock или storage record; соединять Offline-transfer с Online repository. Перенос сильнейшего аффикса принимает только белый предмет-донор.

    Единственный торговый интерфейс находится внутри Godot и обращается к одному версионируемому Economy API. Godot является недоверенным клиентом application-контракта и не получает собственной логики листинга, проверки доступности, резервирования, сопоставления или расчёта. Валютный обмен определён в предметах и крафте; архитектурно отдельный currency order book/matcher ведёт каждую взаимозаменяемую пару независимо.

    Order book владеет заявками, их порядком и результатом matching; Economy wallet/ledger отдельно владеет доступным и предварительно зарезервированным балансом. Каждый fill атомарен и идемпотентен и исключает отрицательный баланс, double spend и overfill. Команды и fills попадают в append-only journal; snapshots ускоряют восстановление, но не заменяют журнал и audit trail. Read-модели книги и лучших курсов могут отставать и горизонтально масштабироваться, однако не владеют балансом или фактом исполнения; versioned events обновляют Godot реактивно.

    Partition key — каноническая валютная пара. У каждой пары есть один логический sequencer/owner, допускающий failover без нарушения детерминированного price-time порядка; глобальной блокировки между парами нет, поэтому backpressure горячей пары не останавливает остальные. Контракт явно возвращает accepted/rejected/retryable outcome, а безопасный повтор с тем же idempotency key не создаёт вторую заявку или fill. Динамический ценовой коридор/circuit breaker может отклонять аномальный курс против передачи ценности и манипуляций; точная формула, fees, expiration, order limits и минимальный fill остаются последующими решениями. Storage, broker, язык, физическая topology, числовая пропускная способность и SLO выбираются после измерений.

    Каталог и фильтрованный поиск являются отдельной горизонтально масштабируемой read-моделью с индексами и кэшами. Она строится из versioned listing events и может временно отставать, поэтому никогда не владеет доступностью лота и не подтверждает покупку. Авторитетный write path повторно проверяет listing revision, eligibility, владение и резерв, гарантирует нулевой oversell и идемпотентный долговечный расчёт. Его контракт явно задаёт поведение при повторе, конфликте, частичной недоступности и backpressure; Godot обязан корректно принять stale/not-available и повторно синхронизировать проекцию. События смены revision и продажи реактивно переводят видимый лот в серое недоступное состояние в Godot, но это ускорение интерфейса, а не доказательство доступности.

    Цель — сохранить быстрый реактивный каталог и покупку при потенциально миллионах одновременно работающих пользователей, размещений и попыток покупки. Это требование к проектированию и измерению, а не текущая гарантия: до реализации команда обязана определить профиль нагрузки и числовые SLO для поиска, создания BuyIntent, розыгрыша, расчёта и распространения событий. Выбор базы данных, очереди, поискового движка, кэша и topology откладывается до этих измерений. Обязательны load/soak/failure-тесты и метрики latency/error/saturation для поиска, intent/draw/settlement и propagation, а также oversell conflicts, retries, reserve failures и fraud/audit signals. Границы identity/auth, rate limiting, listing/buy eligibility и audit предоставляют policy hooks будущей anti-bot-системе; конкретный способ обнаружения ботов пока не задан.

    CURRENT — prototype: server/internal/itemization, itemstore и itempersist уже образуют целевой путь; server/internal/loot и RewardItem — дублирующий legacy-срез. MIGRATION SEAM: anti-corruption adapter превращает старые награды в новые item instances; после миграции оркестратор выдаёт только item IDs. GDD: предметы и крафт.

    Долгосрочная прогрессия¶

    TARGET. Владеет: неторговыми ресурсами открытия и unlock/entitlement игрока, стадиями AI, tier узлов, Memory и прочей метапрогрессией. Изменение проходит серверной транзакцией и audit event. Торговые валютные балансы и резервы принадлежат Economy wallet/ledger, а не прогрессии.

    При создании будущего Online-персонажа эта подсистема атомарно назначает полный учебный Brain-entitlement: все bubbles, все их ступени и улучшения и весь максимум Memory, выдаваемый семью обучающими миссиями и семью испытаниями (14 выдач по +4, текущий потолок 64 — лестница Memory). Контрактом entitlement является вся сумма наград семи миссий и семи испытаний, а не число 64: 64 остаётся значением плейтеста и может измениться, и тогда меняется выдаваемый максимум, а не это правило. Других источников максимума Memory не существует. Выдача эквивалентна завершённой программе обучения программированию и не читает offline-профиль. При этом силовая прогрессия начинается с нуля внутри Online-realm: экипировка, опыт и уровни персонажа, очки и распределение пассивного дерева, доступ к второму билду и его развитие зарабатываются независимо. Ни один из этих источников силы не импортируется из Offline; стартовые числа и точный milestone второго билда остаются versioned balance data.

    Повторный запуск обучающей миссии в Online разрешён, но применение её уже назначенной Brain/Memory-награды идемпотентно и не создаёт дубликат.

    Обещает: snapshot по character/profile ID, проверку entitlement и идемпотентное применение награды/покупки. Требует: identity/profile port, versioned progression rules и подтверждённый результат оркестратора. Запрещено: хранить прогрессию внутри room/session, начислять её из network handler или смешивать offline- и Online-realm.

    CURRENT — prototype: server/internal/game/progression.go хранится через структуры комнаты и обслуживается handler. MIGRATION SEAM: ProgressionService с repository-портом сначала использует memory adapter, затем внешнее хранилище без изменения callers. GDD: прогрессия и idle, мозг персонажа.

    Replay¶

    TARGET. Владеет: сохранением и выдачей канонической записи боя, её индексом и политикой retention. Состав записи и версии схем принадлежат спецификации боевой симуляции: запись хранит версии, seed, стартовый состав, хеши мозгов и внешние команды, а действия ИИ регенерируются из seed детерминированной симуляцией той же версии.

    Обещает: записать завершённый replay, потоково прочитать его и явно сообщить об истечении или несовместимой версии симуляции. Требует: авторитетные входы симуляции, не UI-снимки. Запрещено: telemetry считать replay своим хранилищем, клиенту быть единственной копией результата, воспроизводить запись с несовпадающей версией симуляции.

    CURRENT — prototype: SimulationResult отправляет все snapshots/events, а Godot playback_manager.gd проигрывает их в памяти. MIGRATION SEAM: сначала envelope + codec + memory/file adapter, затем измерения размера определят retention и production storage. GDD: симуляция боя и запись боя, бой и действия, основной цикл.

    Протокол и транспорт¶

    CURRENT — prototype: WebSocket-пакет имеет wire-формат [u16 little-endian opcode][gzip(protojson UTF-8)]; серверная реализация — server/internal/network/packet.go, Godot вручную повторяет opcode и JSON-поля в network_manager.gd. Все области собраны в монолитном shared/proto/game.proto.

    TARGET. Владеет: transport — соединением, лимитами, framing и доставкой; schema packages — wire-visible сообщениями. Доменные системы не зависят от WebSocket, opcode или protojson. Новые контракты вводятся по bounded context и версии (session.v1, combat.v1, items.v1, progression.v1, telemetry.v1); несовместимое изменение создаёт новую версию, поля не переиспользуются.

    Обещает: correlation/request ID, типизированные ошибки, лимиты размера и contract fixtures для Go/Godot. Требует: только application ports. Запрещено: помещать доменную логику в packet handler или молча менять enum/JSON mapping.

Versioned handler и legacy adapter работают рядом; golden packets и end-to-end contract-тесты обязательны перед отключением opcode. Разбиение — средство независимых релизов, а не требование немедленно переписать весь протокол.

    Контент, баланс и визуальный редактор¶

    TARGET. Владеет: content schema, immutable versioned balance packages и процессом публикации. Редактор создаёт draft, но ни редактор, ни runtime не редактируют активный пакет на месте.

    Конвейер: draft -> schema/domain validation -> preview + batch simulation -> review -> staged publish(version) -> activate(version). Сервер закрепляет content version за сессией; новая версия не меняет уже идущую сессию. Hot reload означает загрузку новой версии для новых сессий. Обязательны rollback на прошлую версию, diff, автор/время публикации и воспроизводимый экспорт. Это даёт быстрый цикл баланса без неотслеживаемых live-правок.

    Обещает: resolve stable ID в definition только внутри указанной версии; отчёт валидации и симуляции до публикации. Требует: схемы владельцев, formula kernel и telemetry aggregates. Запрещено: UI и доменным пакетам иметь собственные копии чисел; telemetry автоматически менять баланс.

    Формат авторинга подтверждён: строгий JSON в репозитории, разделённый по bounded context, JSON Schema плюс доменная валидация на Go; Protobuf остаётся только wire-форматом. Раскладка каталогов, состав manifest.json, загрузчик LoadPackage(version) -> ContentSnapshot и порядок публикации описаны в пакетах контента и баланса.

    CURRENT — prototype: definitions и числа распределены по Go, proto и GDScript; отдельного publish pipeline нет. MIGRATION SEAM: сначала inventory всех ID/чисел и read-only package loader, затем экспорт текущих значений как dev-v1, после — редактор поверх тех же схем.

    Realm, identity и persistence ports¶

    Подтверждено: локальное сохранение MVP — SQLite, которой владеет локальный Go-процесс. Godot никогда не открывает базу. Доступ идёт через repository-порты, поэтому онлайновое хранилище позднее заменяет адаптер, а не правила. Детали — в хранении предметов и технологическом стеке.

    RealmContext обязателен на границе профиля и персонажа: offline использует локальную identity/persistence, будущий online — доверенную удалённую. Репозитории и команды всегда scope’ятся realm + profile/character ID; offline-сохранение нельзя прикрепить к Online-account или импортировать в Online. Свободная передача предметов и ресурсов между участниками активной Offline/private co-op-сессии остаётся внутри этого недоверенного realm. В Online межигровая смена владельца предмета принимается только от marketplace service, а не от session, клиента или общего transfer endpoint. Разрешён только узкий перенос декларативного blueprint через общий BlueprintExchange: он не является сохранением персонажа, не несёт прогресс или силу и в Online проходит повторную авторитетную валидацию. Gameplay/application core не знает, где он запущен и какой драйвер хранения выбран.

    Способ Online-аутентификации, account backend, база данных и политика персональных данных GDD пока не задаёт. Архитектура фиксирует порты IdentityVerifier, ProfileRepository, SessionResumeStore, Transaction/Outbox и Clock; для MVP нужны локальные/file либо memory adapters, а не production-инфраструктура. Семантика reconnect зафиксирована: после проверки identity SessionResumeStore восстанавливает привязку к прежнему party slot и character, не создавая нового участника. Конкретного поставщика и срок хранения resume-state выбирают позднее; придумывать их в отдельных подсистемах запрещено.

    Что можно разрабатывать параллельно¶

    После фиксации контрактов первой волны независимы:

    Поток Владеет результатом Может работать со stub
    A. Formula/tags/modifiers math kernel, trace, registries content package
    B. AI/validator compile/validate/decide combat perception, skill catalog
    C. Itemization/persistence item commands и repositories account/content ports
    D. Modes/orchestration state machines режимов combat/item/progression ports
    E. Godot frontend store, reducers, screens, playback recorded protocol fixtures
    F. Protocol/transport versioned schemas, adapters, contract tests application handlers
    G. Content tools schema, validator, package/publish pipeline formula simulation
    H. Observability/replay event sinks, codecs, query/read ports recorded domain events
    I. Dungeon generation algorithms, templates, topology validator mode rules, content package
    J. Online marketplace Economy API, item settlement, pair-partitioned currency matching, catalog/order-book read models item/wallet/identity ports, recorded listing and currency events

    Обязательный порядок предпосылок:

    1. Stable IDs, ownership table и version envelopes.
    2. Formula/modifier contract и content package loader.
    3. Authoritative build resolver и AI validator.
    4. Encounter contract и deterministic replay fixtures.
    5. Mode orchestrators поверх encounter/item/progression ports.
    6. Player-hosted transport adapters и локальная persistence MVP.
    7. Только после MVP — удалённые Online identity/persistence, публичный matchmaking, reconnect и production rollout.

    Интеграционные ворота¶

    Изменение не считается интегрируемым, пока не проходит относящиеся к нему ворота:

    • schema: lint, breaking-change check и golden packet в Go/Godot;
    • content: schema/domain validation, stable-ID uniqueness и reproducible package hash;
    • formula: table tests и trace для stacking/rounding/conversion;
    • AI/build: одинаковые fixtures для editor hints и server rejection, сервер всегда решающий;
    • combat: deterministic seed test, invariant tests и replay round-trip;
    • dungeon: deterministic seed fixtures, topology invariants и проверка всех stable node/template IDs против content package;
    • storage: concurrency/idempotency/rollback tests через один repository contract suite для memory и production adapters;
    • marketplace: contract tests проверяют границу Godot Market UI -> Economy API и запрещают клиенту присваивать логику рынка; load/soak/failure-тесты проверяют заданный load profile и SLO поиска, BuyIntent, draw, settlement и event propagation; concurrency-тесты исключают oversell и проверяют stale revision, retries, conflicts, reserve failure и backpressure; валютный matcher отдельно проверяет price-time priority, multi-counterparty partial fills, IOC/slippage, idempotency, journal/snapshot recovery, failover владельца пары и изоляцию горячей пары;
    • orchestration: state-machine tests для каждого режима; Online intermission отдельно проверяет переход ровно по серверному дедлайну, единогласный fast skip, автоматический голос бота, блокировку fast skip отключённым человеком без блокировки deadline advance, reconnect и идемпотентный повтор команды;
    • frontend: reducer tests доказывают, что server event — единственный источник gameplay-state; Godot smoke-тест проходит полный переход между основными экранами, возврат при пустой и непустой истории, восстановление клавиатурного фокуса и сохранение пользовательских настроек между запусками;
    • observability: сбой telemetry sink не меняет gameplay result.

    Нерешённые архитектурные решения¶

    • размеры групп, PvP combat/rating/reward rules;
    • транспортный адаптер MVP (формат локального сохранения решён: SQLite через локальный Go-процесс);
    • Online authentication/account/storage backend, публичный matchmaking, срок хранения resume-state и поведение после его истечения;
    • конкретный срок replay retention, codec и storage tier — после измерений;
    • deployment topology и гарантии межсервисной доставки;
    • нагрузочная модель и числовые SLO Online-рынка, затем выбор storage/search/queue/cache adapters; fees, expiration, order limits, минимальный fill и точная corridor/circuit-breaker policy обмена валют;
    • числовой баланс, перечисленный в открытых вопросах тематического GDD;
    • остальные незакрытые вопросы собраны в реестре открытых вопросов.

    Эти порты оставлены намеренно. До отдельного решения команда может реализовывать memory/test adapters, но не превращать их поведение в неявное правило игры.
